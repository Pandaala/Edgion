**新依赖**: **需要先解锁** —— 分词器（tiktoken-rs / HF tokenizers）+ 向量能力
（embedding 模型调用 + Redis 向量索引）
**对标**: Kong 3.8+ 语义缓存 / 语义路由 / 语义 prompt guard；Kong 3.11 prompt 压缩；
Traefik proactive token estimation

## 各能力速写

### 1. 主动 token 预估拦截（价值最高，依赖最轻）

Traefik 的差异化点：在请求到达 LLM **之前**估算 token 数，按预算直接拒绝，
而不是等花完钱再事后限流。

- 需要对入站 prompt 做真实分词（字符数/4 的粗估误差在中文和代码上可达 2-3 倍，
  不足以作为拦截依据）
- 与 AI-2 的"事后扣减"策略互补：预估拦截堵住大额单次调用，事后扣减保证账目准确
- 只需要分词器，**不需要向量**。如果只解锁一项依赖，选这个

### 2. 语义缓存

语义相同但措辞不同的请求命中同一份缓存（"北京天气怎么样" ≈ "北京今天天气如何"）。
Kong 的主打降本能力。

- 流程：prompt → embedding → 向量检索 → 相似度超阈值则直接返回缓存响应
- 收益取决于业务的重复率；FAQ 类场景收益大，创作类场景几乎为零
- 风险：相似度阈值设松了会返回语义相近但实质错误的答案，属于**难以察觉的质量事故**。
  必须提供按路由的开关与保守默认值
- 与 AI-1 的 provider 无关 prompt caching（`cache_control`）是两回事，不要混淆：
  后者是 provider 侧的 KV 缓存，不需要向量

### 3. 语义路由

按 prompt 的语义复杂度选模型：简单问题走便宜的小模型，复杂问题走大模型。

- 是 AI-3 负载均衡算法表里明确划归本任务的那一项
- 与语义缓存共用 embedding 与向量索引基建
- 误判代价：简单问题走大模型只是浪费钱，复杂问题走小模型是质量事故，
  阈值应偏保守（倾向大模型）

### 4. 语义 prompt guard

在 AI-4 的规则型 guard 之上，用语义相似度识别变体形式的注入攻击
（规则型只能拦已知措辞，语义型能拦改写过的）。

- Kong 的做法是"语义 guard + 传统 guard 配合使用"，不是替代关系
- 接入点就是 AI-4 的 pipeline，作为一种新的 guard 类型，不需要新框架

### 5. prompt 压缩

Kong 3.11 的能力：去除冗余词句，保留约 80% 语义，宣称最高 5x 成本下降。

- 代价最高、风险最大的一项：压缩是有损的，对指令类 prompt 可能改变行为
- 建议**最后考虑**，且必须默认关闭 + 显式按路由开启 + 提供压缩前后对照日志

### 6. 语义 tool 搜索（2026-08-03 调研新增，向量依赖）

来源：AWS Bedrock AgentCore Gateway（见 [COMPETITIVE-ABSORPTION.md](COMPETITIVE-ABSORPTION.md) 待评估表）。
把每个 MCP tool 的名称、描述、输入 schema 向量化建索引，暴露一个搜索型 tool
（AgentCore 叫 `x_amz_bedrock_agentcore_search`），agent 用自然语言查询，
只把相关的少数几个 tool 加载进上下文。

- **解决的是"工具爆炸"**：聚合了 N 个 MCP server 之后，`tools/list` 可能返回上百个
  工具，全部塞进模型上下文既贵又降低选择准确率。这是 AI-6 §1 聚合能力的**直接后果**，
  聚合做得越成功，这个问题越突出
- 与能力 2/3/4 共用同一套 embedding + 向量索引基建，**不引入第三种依赖**
- 与 AI-6 的关系：AI-6 负责聚合与 RBAC 过滤，本能力负责在过滤后的工具集上做语义检索；
  两者是上下游，不重叠
- 对比参照：agentgateway 的 Code Mode 解决同一问题但走的是"塌缩成单个 `run_code`
  工具 + JS 沙箱"的路径，已明确否决（要在数据面内嵌 JS 运行时）。**语义搜索是同一问题
  的轻量解**——只要向量依赖已解锁，增量成本很小

## 建议的解锁顺序

1. **分词器**（解锁能力 1）—— 依赖最轻、价值明确、无质量风险。
   注意它现在有**两个**下游消费者：本文件的能力 1，以及 AI-2 的事前预估拦截
   （`02-metering-and-cost.md` 开放问题、`04-guardrails.md` §7）。
   AI-2 已收口为"流式增量扣减 + 流末对账"做记账，分词器只用于**输入侧**的事前拦截，
   属于叠加增强而非必需——这降低了分词器的紧迫性
2. **向量**（解锁能力 2/3/4/6）—— 一次投入现在解锁**四**项。
   若 AI-6 的 MCP 聚合先落地，能力 6 会成为向量解锁的新驱动力
3. **prompt 压缩** —— 单独评估，可能永远不做

## 开放问题

- 分词器选型：`tiktoken-rs`（只覆盖 OpenAI 系）vs `tokenizers`（HF，覆盖广但更重）？
  多 provider 场景可能需要按 provider 选不同分词器
- 词表文件是编译进二进制还是运行时拉取？前者体积大，后者引入启动期外部依赖
- embedding 调用打到哪里？复用 AI-1 的 provider 抽象（把 embedding 也当成一种
  provider 调用）是最省事的做法，但会让缓存路径依赖 AI-1 的可用性
- 向量索引用 Redis（LinkSys 已有客户端，`CLAUDE.md` 规定 Redis 必须走
  `RedisLinkClient`）还是允许接入专门的向量库？倾向只支持 Redis，避免第二套存储依赖
