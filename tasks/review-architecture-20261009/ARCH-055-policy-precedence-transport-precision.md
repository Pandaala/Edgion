# Preserve full policy precedence across status seeding and conf-sync

`EdgionBackendTrafficPolicy::precedence_key` reduces `metadata.creationTimestamp` to `DateTime::timestamp()` seconds and then resource name; absent timestamps sort last. Both Gateway EBTP and BackendTLSPolicy stores consume that key. Controller `BackendTLSPolicyState::is_winner`, shared by both policy handlers, compares complete `DateTime<Utc>` values and then raw resource keys. The required oldest-creation-time rule therefore has separate precision contracts.

A supported static FileSystem path retains fractions until policy processing. Canonical EBTP and v1 BackendTLSPolicy YAML is directly deserialized by `parse_resource_content_offline`; the FileSystem controller retains typed clones and passes them into the processor. Without a successfully seeded status sidecar, metadata cleanup and typed status projection do not round creation time before policy parse. Consider valid same-Namespace policies targeting the same Service, `b` at `2026-01-01T00:00:00.100Z` and `a` at `2026-01-01T00:00:00.900Z`, with different effective settings. Process `b` before `a`, with the required Service and route/Gateway ancestor indexes present. After both eligible policies are registered, complete-instant arbitration selects `b`; processing `a` can produce `Accepted=False/Conflicted`. This is a qualified first-processing witness, not a guarantee about arbitrary startup ordering. Initial per-kind files are ordered by complete path, and runtime first applications also enter the serial worker.

The pinned k8s-openapi 0.26.1 `Time` deserializer accepts the chrono instant, but its serializer explicitly uses `SecondsFormat::Secs`. Production ServerCache List and Watch serialization therefore export both creation timestamps as `2026-01-01T00:00:00Z`; the Gateway's actual decoding path cannot recover the discarded fractions. EBTP prepares eligible candidate lists and selects their first entry; BackendTLSPolicy builds valid exact/whole winners in the same precedence order. Both consequently select `a` from these exported candidates. Neither store substitutes the Controller's Conflicted condition for its own arbitration; the resolved target marker establishes eligibility. Sorting complete decoded timestamps alone would still leave this pair tied.

There is a second loss boundary before Controller arbitration: a successful `seed_existing_status` serializes and deserializes the whole resource while inserting only its persisted status. That roundtrip also rounds creation time. Later FileSystem sibling requeues reread the original YAML but can seed the valid sidecar and replace the full instant with its rounded value again. Controller decisions can therefore depend on whether status was successfully seeded and which siblings have been reprocessed. Reprocessing both policies can converge to the name-based winner; this does not establish a permanent split or a fixed divergence duration. The witness is source-derived and has not been executed. Whole-second inputs do not exhibit this precision disagreement, and no Kubernetes deployment incident is claimed.

The correction must retain complete oldest-first ordering. Making the Controller compare only seconds would make later-created `a` beat earlier-created `b`, weakening the governing rule. Existing transport loss does not authorize that change. Rejecting otherwise accepted fractional static metadata would also change the input contract. The useful unification is one Resources-owned full-instant comparison with explicit missing-last ordering and the existing lexical tie break, consumed by both Controller conflict state and Gateway cold policy preparation. Raw namespace/name keys remain the ownership and deletion identity; raw-key and name-only ties are equivalent only within the existing same-Namespace target buckets.

A bounded transport seam is one controller-prepared timestamp value on each of these two policy resources, alongside the existing resolved fields. A small typed value can contain an optional complete `DateTime<Utc>` and use its precision-preserving serde representation rather than Kubernetes `Time`; the inspected locked chrono serializer uses `SecondsFormat::AutoSi`. Distinguish an absent, unprepared value from a prepared value whose source creation timestamp is absent. Keep it schema-hidden with `#[schemars(skip)]` and serialized for conf-sync, without making it an operator field or changing global metadata serialization. Its representation must roundtrip every creation-time value already accepted by the canonical policy ingress, and compare instants rather than formatted timestamp strings.

Preserve the original creation timestamp specifically for BTP and EBTP across successful status seeding before deriving that prepared value. Capturing and restoring those typed policy metadata values around the existing seed follows its existing sidecar-preservation pattern without introducing a generic status or metadata framework. Keep seed failure, ErrorStatus skipping, prior-condition carry-forward and lastTransitionTime behavior unchanged. Both policy handlers must clear any submitted prepared value and rederive it from the preserved source metadata on every parse; Controller conflict state and the exported resource must use that same complete instant. Status history is not a source of timestamp authority.

Gateway preparation must use the exported prepared value with the shared comparator and must not silently treat an unprepared value as a legitimate missing timestamp or fall back to rounded metadata. Retain the existing invalid-candidate/withdrawal semantics for resources lacking required preparation. Include the new value in both stores' explicit resource-equivalence checks and the generation-owned prepared precedence, so a change confined to fractions cannot retain an obsolete resource or winner. Publish it with the existing immutable resource/index/effective generation. This is a bounded cross-crate change to the two schemas, shared comparison, policy status-seed handling, two Controller handlers/state, two Gateway stores and their actual tests. It introduces no request parsing, owned request copies, new lock or lookup. No new generic policy registry or global Time serializer is needed.

Preserve different-second ordering, exact ties, missing timestamps, typed Service/AI separation, BTP section identity and exact/whole occupancy, complete eligibility, invalid-policy withdrawal, sibling promotion, Service fan-out, AI-only target bounds, atomic winner sections, captured old snapshots and equivalent-update runtime handles. Fraction-only source changes must participate in the existing precedence-relevant sibling requeue and old/new target publication; full and partial publication must choose the same winner. Retain one queue/worker, all runtime reprocessing through requeue and inline status persistence. TLS/Secret ownership and redaction remain unchanged, with no new logs or metrics.

Future verification must use the actual static parser and processor with absent, invalid and successfully seedable sidecars; compare preserved source timestamps and real ancestor conditions. Serialize processed policies through the production List and Watch boundary, decode them through the Gateway path, and assert that both policy kinds select `b` for the reversed-name fractional pair before and after ordinary requeues. Cover fraction-only changes, different seconds, exact ties, missing timestamps, winner removal, invalid withdrawal and full/partial equivalence; retain Arc/generation and condition-transition regressions. Existing selected Resources precedence, Controller conflict/status-seed, and Gateway winner/promotion test bodies use whole-second precedence dates or test the seams separately; they do not establish this cross-boundary invariant. No test was run.

Original oldest-wins, EBTP atomic-snapshot, AI-only target-bounds, BTP incremental-publication and typed-key/requeue decisions remain applicable. Some resource architecture prose still describes unconditional on_change sibling requeue, while current handlers gate it during parse; that stale description supplies no authority to redesign the queue. ARCH-023 addresses replicated prepared target ownership and ARCH-024 addresses final-key delta normalization; ARCH-016/018 concern different backend lifecycles. This finding is the inconsistent ownership and preservation of policy arbitration time. Its benefit is stable status/runtime agreement for the existing ordering rule, not a measured performance gain or a general timestamp cleanup. Fresh source/support hashes and actual read scopes are supplied in the independent verification receipt.
