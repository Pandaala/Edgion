# Require an observed HTTP rejection in the excessive-XFF probe

`SecurityTestSuite::test_excessive_xff` in `edgion-tests/src/client/suites/gateway/security/security.rs` owns a byte-limit rejection assertion, but its `request.send().await` error branch unconditionally returns `TestResult::passed_with_message`. The comment labels connection resets and similar errors acceptable, while the match actually admits every reqwest error, including connection establishment failure before the request reaches the Gateway. A listener that becomes unavailable between the normal-XFF case and this case therefore produces a passing `excessive_xff_length` result without exercising XFF admission. This is a source-derived false-positive witness, not a claimed live incident. The other cases can still fail; no claim is made that a wholly unavailable stack passes the complete suite.

The intended request has a valid `/health` path and `test.example.com` Host. Its twenty `203.0.0.<i>` entries form a228-byte ASCII XFF value, exceeding the actual fixture EGC's200-byte limit. The local and Kubernetes Security fixtures select the same HTTP listener and route to the real health backend. The shared runtime snapshot supplies the byte limit, and `snapshot_x_forwarded_for` compares the aggregate field length against it. After earlier path/Host validation, `build_request_metadata` records `XffHeaderTooLong` and awaits `end_response_400`. For this ordinary HTTP request, the canonical response writer commits HTTP400 and writes the fixed error body before shutdown. This contract does not intentionally substitute an unclassified connection error for the rejection response. Actual unit bodies cover exact aggregate limits, invalid bytes counting toward the limit, earlier Host/path error precedence, and over-limit rejection through the production seam.

Targeted Gateway/Security, aggregate Gateway and the full suite register this same case through the existing listener-selection machinery. The normal, boundary and no-XFF cases already fail sending errors. Their success is useful readiness evidence but cannot attribute a subsequent failed connection to the XFF policy. The current oversized case's explicit400 branch supplies the appropriate acceptance boundary; the unconditional error-pass branch discards that boundary precisely when there is no observed response.

Make this existing negative case fail request-construction, connection, transport and deadline failures, and pass only on the intended HTTP400 response from the selected listener. Keep its228-byte request,200-byte threshold, logical Host, canonical context URL and existing thirty-second TestCase deadline. Preserve the other three case identities and their current normal/boundary/no-header meanings. If a separately designed supported transport later rejects this input without an HTTP response, establish that exact Gateway-originated outcome through a narrow protocol witness before adding it; broad reqwest Display text or error category alone does not establish policy rejection.

The bounded improvement belongs to this test's outcome classification. It requires no production security change, listener topology, generic negative-test framework, new logs or metrics, access-log payload disclosure, extra dependency or changes to request BodyStorage and response streaming. A healthy control alone is an insufficient alternative because the tested connection can fail afterward. Keeping all connection errors accepted perpetuates an assertion whose reported policy success can occur before the policy is evaluated.

Future verification should preserve all four case identities and show that an unavailable listener fails the excessive-XFF case, an actual400 succeeds, a non400 response fails, and the normal/exact-boundary requests still succeed against the existing200-byte fixture. Read the original integration assertion/listener contract, current HTTP1 ownership decision, actual snapshot/rejection writer and unit bodies. Searches of current findings and pending task pages found no existing XFF-specific outcome correction. ARCH338 concerns a different kind-denial protocol boundary and ARCH283 server-authentication probes; neither owns this HTTP byte-limit case. All evidence here is static repository source; no tests, services or network calls ran.
