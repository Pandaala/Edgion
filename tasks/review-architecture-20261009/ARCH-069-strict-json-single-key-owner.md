# Use the strict JSON result object as its duplicate-key owner

Resources owns one strict JSON instance parser in edgion-resources/src/resources/edgion_plugins/plugin_configs/json_schema_validation.rs. ValueVisitor::visit_map at lines365–390 constructs both the returned serde_json::Map<String, Value> and a separate HashSet<String>. Every decoded key updates text accounting, is cloned into the set, and is then moved into the result map after its value parses. Each object therefore retains a second key payload and a second key index throughout that object's parsing. Recursive parsing can keep ancestor sets alive while nested objects allocate their own sets. These are source-observed temporary owners, not a measured peak-heap or throughput result.

The cost reaches production request paths. JsonSchemaValidation::run_request calls parse_json_instance after canonical body admission/materialization (Gateway plugin.rs94). GraphQL POST and GET variables/extensions call parse_json_instance_with_limits through Resources graphql_request/envelope.rs39–42; Gateway common/graphql_request.rs76–188 holds the canonical evaluation permit while parsing. BoundRequest::encode in Resources grpc_transcoding/codec.rs43–59 uses the parser before request merge/normalization. ProxyRewrite plugin.rs408 and FormJsonTransform plugin.rs288 use the same parser for bounded request transformations. This proposal changes only that canonical parser, not their body or response ownership.

Duplicate rejection is necessary, and the DOM must own decoded keys because consumers retain and inspect it. A separate retained copy of the same keys is unnecessary: previously committed fields already constitute the duplicate inventory for the current object. The representation makes a future object-parser change reason about two membership owners even though only the returned map survives success.

Use the pinned serde_json Map::entry API with the decoded String moved into the entry. Keep text accounting before duplicate detection. An Occupied entry must set the same sticky DuplicateKey failure and return the same fixed error before reading that duplicate's value. For a Vacant entry, call the unchanged next_value_seed with the shared ParseState and depth+1, then insert the parsed value through that vacant entry. Do not insert a placeholder or parse the duplicate value first.

Cargo.lock pins serde_json1.0.151. Its map.rs273–289 moves Into<String> into the backing map entry; Entry623–648 and VacantEntry::insert788–789 support this boundary. The lock's serde_json dependency list has no IndexMap/preserve_order edge, and the default map backend is BTreeMap. The public entry interface also supports the alternate backend without selecting a new feature. The vacant entry borrows only the local parent result map. Recursive value parsing borrows the separate ParseState and deserializer and creates its own nested maps; it does not need access to that parent map. A parsing failure drops the vacant entry and partial object through normal ownership. This is static API/lifetime feasibility, not a compiled implementation proof.

This removes the parser's per-object HashSet and cloned key strings, while retaining decoded String keys, values and the final map's own allocation. Other HashSets used by schema validation retain their independent purpose. A contains_key check followed by insert is a smaller alternative that also removes copied keys, but repeats result-map lookup. Removing strict duplicate checks or using ordinary Value deserialization changes semantics and is not an alternative. No new parser, global interning, borrowed DOM, request cache, allocator trick or generic JSON framework is needed.

Preserve UTF-8/escape decoding, equality of decoded keys (including differently escaped spellings), nested-object independence, malformed/trailing-data and number behavior, fixed error classifications, depth/node minima against caller-selected bounds, saturating text accounting and the absolute1MiB input cap. Preserve generic JSON Schema replies, mutation transactions, GraphQL64KiB envelope and carried Work/four-permit lifetime, transcoding admission and all callers' tighter limits. BodyStorage remains the only proxied request-body owner; streamed responses and bounded unary conversion exceptions remain unchanged. No key/value content, new request tracing or metrics may be emitted.

Existing strict-parser tests were fully read: duplicate/depth/trailing-data rejection, node/text counts, node and byte overflow, private-token object keys and validator work/profile cases. GraphQL strict-envelope tests also reject duplicate query fields. Gateway JSON Schema tests retain fixed400/413/415/500 outcomes and pre-materialization ordering. Future verification should distinguish escaped-equivalent and nested duplicates, duplicate-before-malformed-value/depth/node precedence, unchanged accounting for valid nested objects, and cleanup after partial failure. An allocation check may isolate large-key objects, but must not mistake remaining DOM/source allocations for a failure or claim a process RSS bound.

Original GraphQL cost/guard/safelist/router decisions and the JSON Schema operator contract require strict bounded parsing; none requires a second retained key inventory. ARCH050 covers repeated cold configuration validation; ARCH053 covers cold-resolved GraphQL field coordinates; ARCH061 concerns operator CustomField source arity and explicitly excludes earlier generic Value duplicate collapse. These are different causes. Static read-only review only: no tests, builds, benchmarks, runtime probes or source changes.
