# ARCH-304 — Complete Kubernetes execution ownership for the five GraphQL and transcoder dynamic scenarios

Five registered local dynamic scenarios have no executable Kubernetes counterpart or approved scope exception: GraphqlGuardDynamic, GraphqlOperationRouterDynamic, GraphqlRateLimitDynamic, GraphqlSafelistDynamic and GrpcJsonTranscoderDynamic. Their local phase suites exercise real admission, dependency and data-plane transitions, but publishing these scenarios did not complete the existing Kubernetes inventory and fixture ownership contract. This leaves five concrete holes in the canonical dynamic parity gate. It does not establish a production defect or claim that a current complete Kubernetes run passed.

The primary declaration sites are edgion-tests/src/client/dynamic/scenarios/graphql_guard.rs:164-169, graphql_operation_router.rs:87-92, graphql_rate_limit.rs:113-118, graphql_safelist.rs:57-62 and grpc_json_transcoder.rs:42-47. All five are included in dynamic::all and test_client.rs::EXPECTED_DYNAMIC_SCENARIO_IDS. Their run functions and actual phase suites cover guard limits and metadata validation, declared GraphQL backend changes and ReferenceGrant changes, cost-model and root-quota validation/recovery, safelist rejection/revocation, and descriptor invalidation/deletion/recovery. These are meaningful assertions to preserve, not names that can be removed to satisfy inventory parity.

The Kubernetes execution owner is separate. run_k8s_integration.sh:2164-2220 derives expected dynamic results from k8s_dynamic_scenarios.tsv, invokes the manifest-backed helper and rejects incomplete results; the full-run branch calls it at 3005. run_k8s_dynamic_scenarios.sh:88-192 selects manifest entries and validates their real fixture/reset directories, and its execution loop at 943-990 invokes those selected IDs after staging the Kubernetes conf tree. The main script also directly invokes AiBackendPolicyIntegration at 2161. That direct invocation proves why absence from the TSV alone is insufficient evidence. Current searches of the complete main script find none of the five IDs, and none appears in the manifest or scope-exception table. None of their EdgionPlugins/GraphqlGuard, GraphqlOperationRouter, GraphqlRateLimit, GraphqlSafelist or GrpcJsonTranscoder fixture trees exists in edgion-tests/k8s/conf.

The existing validator explicitly owns this distinction: validate_suite_parity.sh:145-166 reads the canonical local constant and direct Kubernetes calls, 169-222 parses manifest IDs, and 372-413 unions direct calls with manifest entries before subtracting validated scope exceptions. Missing canonical IDs make the validator return failure. This review read that implementation and its actual shell regression tests; it did not run the checker or infer that other current inventory gaps are absent. The finding is confined to these five primary-owned scenarios, not a promise that adding them alone makes the repository-wide parity check pass.

A row-only repair would still be invalid. The local GraphQL backend fixtures use manually authored EndpointSlices with 127.0.0.1 addresses; the Kubernetes runner stages only Kubernetes fixtures and enforces selector-owned endpoint inventory. The operation-router phases also require distinct users/orders backends and the graphql-other cross-namespace target, so substituting one generic echo backend would weaken its identity and grant assertions. GraphqlRateLimit fixtures refer to default/redis-test, whereas the existing Kubernetes Redis LinkSys and working RateLimitRedis fixture use edgion-default/redis-test. Reuse that in-cluster dependency with the correct reference and retain fresh request keys; do not flush Redis or introduce another dependency lifecycle.

There is also an actual transport migration seam. The Kubernetes helper's default target is the Gateway Service DNS name, but suites/edgion_plugins/grpc_json_transcoder.rs::call_traced:28-43 parses target_host strictly as IpAddr and returns "fixture target must be an IP" for that supported default. The test framework and ScenarioCtx already have test-target DNS resolution mechanisms. Adapt this test-owned request helper to the existing resolved target and selected HTTP listener port while preserving its logical host, explicit H1/H2 modes, trace markers, deadline and response assertions. This is part of making the declared Kubernetes entry executable, not permission to add a production DNS resolver or change transcoder transport behavior.

Complete the bounded publication seam for these five IDs: create Kubernetes-owned initial, update and reset fixtures preserving the existing object identities and phase behavior, provide selector Services to the existing real test-server backends, reuse the existing Redis LinkSys, and register each scenario through the current seven-field manifest with the appropriate primary-resource convergence barrier. Keep the existing helper's before/after restoration, endpoint validation, capability propagation and result-protocol checks. The three current body-buffering capability entries for GraphqlOperationRouterDynamic, GraphqlRateLimitDynamic and GrpcJsonTranscoderDynamic remain in force; unsupported explicit selections must still fail. Do not replace explicit dispatch with a registry framework, suppress the parity check, delete local IDs, or add blanket exceptions for features supported by the current product.

The real GraphQL and transcoder status phase suites currently use the shared complete-resource fetch and then index native status.conditions. Kubernetes EdgionPlugins observations require the selected Controller projection. ARCH266 already owns that assertion-input root cause; these newly registered readers are additional same-cause migration sites, not a second finding. Keep that projection correction separate and reuse the canonical test-owned selection without flattening the Controller API. Likewise, ARCH264 owns scenario initialization/restoration across direct invocations and failed transitions; the existing Kubernetes wrapper already provides its own reset path. Completing this execution inventory does not replace either correction or justify weakening their assertions.

A narrowly evidenced environment exception remains a legitimate alternative only when the original assertions cannot currently be supplied in Kubernetes. Existing exceptions are specific to ACME status seeding and encrypted-health certificate/listener fixtures; they do not cover these five scenarios. Current Services, selector-backed HTTP/gRPC test servers, ConfigMap/EdgionPlugins apply and deletion, cross-namespace ReferenceGrant fixtures and Redis LinkSys show feasible mechanisms for these features. The original kubernetes-dynamic-scenario-inventory-parity and kubernetes-dynamic-fixture-boundaries pages require an executable entry with real fixtures or a justified exception, and explicitly say a row alone is not coverage. Their earlier 55/55 verification is historical evidence for the previously listed scenarios, not verification of these five later declarations. The two referenced parity task files are absent from the current tree; the retained knowledge contract is not an invented current implementation authorization.

Future implementation verification should run the existing inventory/helper regressions, retain a negative case for a canonical ID absent from both direct calls and the manifest, and execute all five complete phase sequences against current Kubernetes images. Verify real backend identities, correct selected Controller conditions, invalid-admission and recovery outcomes, safelist revocation, cost/quota changes, and descriptor deletion/recovery over the original downstream protocol contracts. Exercise failed transitions and reset failures without hiding their outcomes; retain authenticated admin calls, redaction and canonical access-log evidence. Preserve request-only BodyStorage, streamed ordinary responses, the independently bounded unary transcoder exception, supported BoringSSL behavior and the existing serial Controller workqueues. No build, checker, test, network operation or repository mutation occurred, and no timing, performance or incident claim is made.
