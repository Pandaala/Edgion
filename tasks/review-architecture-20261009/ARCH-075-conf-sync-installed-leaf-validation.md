# Bind conf_sync identity validation to the certificate installed by the transport

The shared validate-before-swap owner in edgion-common/src/grpc_tls.rs parses the first PEM block with x509_parser::pem::parse_x509_pem and calls parse_x509 on its DER without checking its label. Controller ServerIdentity::from_pems uses this gate, then obtains validity and serial from the same first-block policy, but builds its serving chain with rustls_pemfile::certs, which filters out non-CERTIFICATE blocks. Its file watcher installs the resulting identity after from_pems succeeds. Thus validation and metadata can describe a different certificate from the actual serving leaf.

A distinguishing static witness is a currently valid CA-signed certificate A relabeled PUBLIC KEY, followed by an expired CA-signed CERTIFICATE B using the same public/private key and CA. The separate key and CA inputs are valid. Locked x509-parser 0.18.1 parses A's DER regardless of its label, so current validity, signature and private-key checks apply to A. Locked rustls-pemfile 2.2.0 wraps the PUBLIC KEY payload without validating it as SPKI and filters that item from certs, selecting B as the first serving certificate. Locked rustls 0.23.45 with_single_cert calls CertifiedKey::from_der and keys_match: these check parsing/key consistency, not the serving certificate's current validity. Same-key B therefore survives the constructor's key check. This is a source witness, not an executed exploit or observed deployment incident.

The Controller file reload path reads candidate bytes, calls from_pems, then handle.store. Under the witness it can replace a valid serving identity with an expired leaf while retaining A's validity and serial. Normal peers may reject B, and the installed metadata does not describe B. No client-authentication bypass or remote ability to write these operator-owned files is claimed. The documented invariant is nevertheless validate-before-swap with last-good retention: an invalid replacement must not take the serving identity offline. The shared API comment and current link architecture explicitly impose that invariant.

Keep the improvement bounded to selection consistency. A conservative fix is to require that the first decoded leaf and CA PEM blocks at the shared reload/provision gate have the CERTIFICATE label, using fixed diagnostics. This preserves the Controller's existing first-block metadata policy for accepted normal certificate inputs and rejects a prefix that the transport would skip. It does not broaden the validator to seek a later certificate, does not turn initial lazy client construction into a new admission gate, and does not alter trust-root bundle membership or full-chain policy. Another feasible design would jointly select transport certificates and derive validation plus Controller metadata from that selection; changing only the validator to first-CERTIFICATE selection is insufficient.

The original installed-certificate-expiry regression guard records exactly that coordination hazard: initial client loading intentionally selects the first CERTIFICATE even after other labels, while reload/provision validation and Controller metadata were left on their original policy. An intermediate validator-only change was withdrawn. That is evidence against a unilateral selector migration, not acceptance of validating an unrelated relabeled object before serving a different leaf. Preserve the initial client's existing mixed-prefix validity behavior and immutable Channel/validity publication. Audit the current shared validator callers in Gateway cert reload and Controller provision, rotation and ServerIdentity construction when changing this gate; normal CA/leaf files continue to work, and invalid candidates retain their existing refusal, rewrite or last-good outcomes.

Existing actual Common tests cover valid identities, expired leaves, wrong CAs, mismatched keys and garbage; Controller identity tests cover metadata, h2 ALPN, root retention, atomic replacement and same-root versus root-change cancellation. None distinguishes a valid non-CERTIFICATE prefix from the expired same-key certificate actually selected by transport. Future focused coverage should establish that the witness is rejected before store, with the old identity, validity, serial and trust token unchanged, while ordinary leaf-first chains and initial mixed-prefix client construction retain their current contracts. Include a wrong-label CA rejection without echoing PEM markers or contents. No new metrics, request logs, dependency, generic certificate registry or Gateway rustls backend support is needed.

The alternative of changing only expiry reporting would still install an unvalidated leaf. Broadly unifying ordinary EdgionTls/BoringSSL chain validation, conf_sync root rotation and client lazy loading would expand policy scope without being necessary. Retain existing chain/signature/key validation, inclusive validity semantics, Controller leader/replica rotation ownership, same-root continuity and trust-root cancellation. Ordinary request BodyStorage, response streaming and binary observability ownership are unaffected.

Classification: behavior-defect, P2, because the shared safety gate can admit a different invalid serving certificate and break last-good retention under deliberately constructed operator material. The benefit is one defensible accepted-input invariant across validation, metadata and installation. All evidence is read-only source and existing test inspection, including locally cached locked dependencies; no fixtures were generated, builds/tests executed, files deployed or network handshakes performed.
