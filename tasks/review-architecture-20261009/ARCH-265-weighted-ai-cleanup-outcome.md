# ARCH-265 — AI backend scenario cleanup failures must affect their results

Three AI backend dynamic scenario owners discard every Result returned by TestContext::delete_resource: ai_backend_weighted.rs::cleanup at 278-292, ai_backend_lifecycle.rs::cleanup at 437-461, and ai_backend_policy_integration.rs::cleanup at 890-914, all under edgion-tests/src/client/dynamic/scenarios/. Each invokes cleanup before its business transitions and again afterward. Weighted's run at 416-423 and PolicyIntegration's run at 1135-1142 return only run_inner's outcome. A successful traffic/status matrix can therefore be reported as passed even when final resource deletion failed.

Lifecycle has meaningful additional safeguards that must be preserved. Its run at 962-994 waits for both owned EdgionBackends to disappear before capturing the shared store-count baseline. After transitions and final cleanup, it again waits for those two backends to disappear and for the total edgion_backend_store count to stay at or below that baseline. These checks detect backend residue or unavailable Gateway observations; this finding does not claim that every owned key lacks a cleanup guarantee. However, successful backend absence/count checks do not establish successful deletion of its remaining policy, ReferenceGrant, HTTPRoute, plugin, Service and Secret keys. The DELETE results for those keys are still discarded.

This is one failure-result ownership defect across three scenario files, separate from ARCH264's missing restoration path. These owners already call cleanup after either returned business outcome. TestContext::delete_resource at framework.rs:454-485 performs an authenticated Admin request with a five-second timeout and returns Err on client construction, transport failure or any non-success status. It reads the error response body into a formatted String. An absent resource also produces a 404 error: delete_namespaced delegates to the writer, the writer's NotFound maps to HTTP 404, and a successful deletion returns 204. Consequently, simply propagating the first existing helper error would incorrectly fail normal cleanup of an initially absent topology and abandon later keys.

Weighted declares nine cleanup keys: its ReferenceGrant, parent and child HTTPRoutes, EdgionPlugins, zero-weight Service, two EdgionBackends and two credential Secrets. Lifecycle declares fifteen keys, including optional policy names, and PolicyIntegration declares fourteen keys covering its TLS/traffic policies, routes, plugin, backends and credentials. Preserve each explicit list and its current order. A concrete Weighted or PolicyIntegration witness is successful run_inner followed by an unavailable Admin endpoint or one non-404 rejected deletion: cleanup discards the error, run returns Ok, and test_client.rs::run_dynamic_scenario prints passed. For Lifecycle, a narrower witness is a failed final Secret or route deletion while its backend deletions and existing absence/count observations succeed; that surviving non-backend failure does not affect the returned successful business result. These are source-level permitted failure interleavings, not executed outages or claims that all cleanup keys survive.

Make each cleanup return a fallible aggregate outcome. Attempt every declared key, accept actual HTTP success and 404 as idempotent absence, and collect non-404 status or transport failures with safe operation/key context. Use the existing test-owned EdgionClient response API or the concrete response-status loop already used by AllEndpointStatusTls; do not infer 404 from formatted error text or weaken the general delete helper. Preserve authentication, endpoint selection and bounded transport. Do not include response bodies, Secret content, bearer tokens or unsanitized transport URLs in the collected diagnostics. The response-status pattern is a reuse seam, not a claim that copying every existing error formatter is safe.

Capture initial cleanup, existing initial observations and business execution as the scenario result; a failed initial cleanup must prevent setup from proceeding. Keep final cleanup outside that result so it attempts all owned keys after either success or failure. In Lifecycle, retain the initial two-backend absence barrier and baseline capture, and retain the final two-backend absence and total-count postconditions. Attempt those final observations even when the deletion aggregate reports failure, rather than allowing a new early return to bypass them. Compose the captured scenario result, deletion outcome and existing convergence outcome so cleanup failure fails otherwise successful assertions and simultaneous business/cleanup failures retain their distinct safe contexts. Lifecycle's current cleanup_result? also loses the prior business error when its postcondition fails; the same local result composition can preserve both without weakening either assertion.

The bounded change preserves weighted sampling and its existing entropy inputs, denied/missing slot failure shares, zero-weight exclusion, delegation, header modifiers, reference/grant transitions, typed policy arbitration, Secret rotation, TLS/SNI/SAN/mTLS checks, in-flight capture, stream termination assertions and all fixture-manifest tests. It adds no generic cleanup framework, new process/topology, product behavior, log or metric. Existing downstream absence checks remain intact. Adding complete per-key Gateway convergence checks to the other owners is a separate stronger postcondition; this finding requires truthful operation failure reporting and does not claim that a successful DELETE proves immediate Gateway convergence.

Best-effort attempts with a returned aggregate are preferable to stop-at-first-error propagation, which abandons later keys. A final fleet residue gate is weaker because direct scenario invocation has no such gate and later suites can run before it. The Kubernetes wrapper's run-scoped reset and failure reporting remain independently necessary; they do not justify discarding failures inside the Rust scenario.

Original integration lifecycle rules require setup/teardown errors to affect the result, and the dynamic guide requires cleanup after success and failure. Accepted local single-owner takeover does not relax failure reporting; Kubernetes ownership and containment remain unchanged. The complete three scenario implementations and their actual unit-test bodies, existing cleanup pattern, delete response owner and runner seams were read. Future focused verification should cover initially absent keys, successful deletion, a non-404 failed deletion after successful business assertions, and simultaneous business/deletion failures while proving all later keys were attempted. For Lifecycle, include failed non-backend deletion with successful existing backend/count checks and preserve a failing convergence outcome alongside a failing matrix. No test, build, network operation or repository mutation occurred.
