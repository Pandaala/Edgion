# Validate ExtProc targets against the URI the cold client actually constructs

The schema-owned `validate_target` accepts a nonempty host containing spaces. For the otherwise default configuration `grpcService: { target: "ext proc:9000" }`, it finds a nonempty host, parses the valid port, and returns success; the default timeout and processing modes also pass `ExtProcConfig::validation_error`. Gateway `ExtProcClient::new` then splits the same target, lowercases the host without removing the space, and passes `http://ext proc:9000` to `tonic::transport::Channel::from_shared`. The locked tonic 0.12.3 implementation calls `http::Uri::from_maybe_shared`; locked http 1.5.0's authority parser rejects ASCII space as `InvalidUriChar`. This failure happens during cold URI construction, before the lazy connector makes a network connection. It is not a DNS, TLS, dependency-availability, or egress-policy failure.

This contradicts the documented purpose of `validate_target` in the current source: catch malformed targets at Controller ingest instead of letting channel construction seal the route with 500. The actual shared path is `EdgionPlugin::validation_error` → `ExtProcConfig::validation_error`; `EdgionPlugins::validate_plugins_before_waf_resolution` invokes it for enabled request entries, and `EdgionPluginsHandler::preparse` returns those errors to the processor. `update_status` sets Accepted=True when validation errors are empty. A plain ExtProc-only entry with this target therefore has no target error for Controller status. Lenient admission still syncs invalid configurations, so status is advisory rather than the serving gate.

The Gateway independently validates entries, then calls `ExtProc::create_attached`. For this input, the same shared validator passes, client construction fails, and `create_attached` returns None. `PluginRuntime` records `plugin construction failed`, marks ExtProc invalid, and seals the runtime with `RejectInvalidConfig`; that filter returns the existing generic HTTP 500. `failureModeAllow` does not change configuration rejection into dependency fail-open. This is not evidence of a Kubernetes incident, and the finding does not assert a security bypass or an absence of runtime protection.

Make the ExtProc field owner enforce representability of the effective authority used by the cold client. Keep the existing bare-target checks and port range, split bracketed hosts exactly as today, and validate the complete effective `http://{normalized_authority}` URI with the existing `http::Uri` parser rather than inventing another hostname grammar. An authority-only parse is insufficient: the locked URI parser also bounds the complete URI to `u16::MAX - 1` bytes, including the seven scheme bytes. Resources already depends on `http`; it needs no Gateway or tonic dependency. A narrowly scoped shared ExtProc target parser/projection can return the host, port, and effective authority for Gateway construction, replacing its duplicate split/normalization only where that establishes the same field invariant. Alternatively, a private schema check may validate the same effective URI while leaving the transport projection in Gateway; the required outcome is identical static representability, not a general endpoint abstraction.

Preserve the currently accepted target forms that survive the existing transport: discovery aliases and single-label hosts, IPv4, bracketed IPv6, unbracketed IPv6 currently normalized by `IpAddr`, case normalization, and supported nonzero ports. Validating the raw unnormalized target directly as an authority would accidentally narrow the unbracketed IPv6 contract and is not an acceptable shortcut. Keep the field's current rejection of URL schemes and path/query/fragment; preserve both plaintext and TLS channel configuration, including the custom TLS connector's deliberate `http://` channel URI. Do not expand TLS identity support, alter effective TLS inheritance or fingerprint/cache/egress/DNS owners, add network validation, or change the native ExtProc SDK protocol, mode reductions, request-only BUFFERED support, or response BUFFERED prohibition.

Return a fixed field diagnostic for invalid URI characters without echoing the configured host or raw parser error. Add focused schema and cold-constructor parity coverage for an embedded ASCII space/control character, representative accepted forms, and the effective complete-URI length boundary. An enabled plugin wrapper should report the target-specific validation error before construction, and Controller status should classify the static input as Invalid. Preserve the existing generic fail-closed serving boundary as defense in depth. No new request logs or metrics are necessary.

Existing resource target tests cover empty host, URL/path/query/fragment, missing or invalid port, zero/out-of-range port, malformed brackets, and valid bracketed IPv6, but omit invalid host bytes. The original ExtProc unsupported-TLS-identity guard confirms that configuration rejection is independent of `failureModeAllow` and retains generic sealing; the interactive-processing guard separately owns body/phase semantics. Neither accepts a target that cannot be represented by the actual channel URI. This cause is separate from ARCH-064/065's other field owners and ARCH-050's repeated invocation validation.

The useful change is early, actionable static validation and Controller/Gateway agreement. A broad DNS-name validator, generic target registry, new TLS implementation, or new outbound client is unnecessary. This is a bounded admission-parity behavior finding, priority P3. Evidence is source inspection of the real call chain and pinned dependency parser; no configuration application, network connection, builds, or tests were executed.
