# Retire the legacy singular TLS owner from the shared channel-security contract

ConfSyncSecurityConfig in edgion-common/src/conf_sync/config.rs still owns a serialized/deserialized tls: Option<ConfSyncTlsConfig> alongside certs and active. resolve_active_tls falls back to tls when certs is empty; is_plaintext_omitted and the dangling-active validation guard also inspect it. Startup guidance still recommends the legacy block, and ConfSyncTlsConfig::validate names conf_sync_security.tls fields even when validating a canonical certs entry. This is a live parallel configuration model, not an unused type alias.

The current original Controller/Gateway link architecture and both binary configuration schema pages explicitly identify the singular field as pre-release removal debt and define certs plus active as the current file-mode contract. Root AGENTS.md imposes no historical compatibility burden. These are requirements to check against current sources, not proof that current deployments already use the desired representation: they do not. config/edgion-controller.yaml, config/edgion-controller-etcd.yaml, config/edgion-gateway.yaml and cicd/deploy/kubernetes/gateway/configmap.yaml still configure tls. Standalone and packaging defaults, isolated Kubernetes proxy configurations and the integration security-block generator also emit it. Current executable defaults therefore perpetuate the schema debt that current architecture tells developers not to extend.

A concrete selector witness shows the maintenance cost of the dual owner. With otherwise valid file paths, certs=[], active="ghost", and legacy tls present, validate does not search for ghost because its lookup is conditional on nonempty certs. The dangling-active guard also does not fire because tls is present. resolve_active_tls then returns the unnamed legacy set and ignores ghost. The corresponding canonical certs configuration rejects a nonexistent selector. This is a static source witness of two inconsistent selection models; it does not establish a plaintext downgrade, failed mTLS handshake or production incident. Both valid file-mode paths still load TLS material.

The production consumers already converge on the shared selector, so another transport abstraction is unnecessary. Gateway CLI validates security and enforces configured transport before ConfigSyncClient::new independently resolves the active set for lazy channel construction, installed validity and reload file paths. Controller CLI validates and enforces the block before startup, then uses the shared selector for its file-based serving identity and cert watcher. Its plaintext serving gate resolves the same block. The retained Controller federation client uses the same ConfSyncSecurityConfig through CenterClientConfig.security, validates it, requires resolve_mtls_or_refuse and loads selected material through the canonical common gRPC TLS loader. No repository production consumer needs direct access to the legacy field. The external Center server is not in this repository and is not part of the proposal.

Remove the singular field and its fallback/omission/selector branches from this one shared owner. Keep certs and active as the file-based representation, including the existing single-entry automatic selection and multi-entry explicit selection rules. Migrate current executable configurations, test fixture constructors and generated transport blocks to this representation in the same bounded change. Update current startup remedies and configuration references so they no longer direct operators to the retired field. Preserve historical plaintext-fix evidence as history while correcting its current configuration examples. Do not add a deprecated re-export, auto-conversion shim, second parser, generic channel factory or repository-wide unknown-field policy.

The migrations are necessary for correctness, not a follow-up cosmetic cleanup. Deleting only the struct field would cause the current legacy-only defaults to deserialize without a selected certs entry and fail their transport guards. The ordinary three root YAML defaults must retain exactly their existing server/client certificate, key and CA paths. The Kubernetes Gateway must retain auto_ca and the same mounted client paths in a selected certs entry; the Controller's bare auto_ca provisioning shape must remain valid. Standalone and packaging copies and the two isolated proxy configs require the same field-preserving rewrite. The integration conf_sync_security_block helper must emit canonical file-mode entries, while conf_sync_replace_with_skip_tls must still emit an explicit selected plaintext entry without dummy paths. run_conf_sync_mtls_test.sh already runs with multi-cert configs; its extra legacy compatibility-only YAML emission is unused by the automated run and can be retired rather than kept as a new compatibility contract.

Preserve the load-bearing transport distinctions: omitted security must refuse the Secret-carrying conf_sync channel; explicit selected skip_tls remains the emergency escape hatch with existing diagnostics; file-mode paths keep work-directory resolution; Controller bare auto_ca retains its provisioning behavior while Gateway auto_ca requires mounted paths. Federation still refuses omitted or skip_tls security and degrades its auxiliary client rather than crashing the data plane. Certificate validation, live installed identity/validity publication, watcher signatures, generation cancellation, trust-root revocation and per-replica versus leader rotation remain their existing owners. The observed Controller auto_ca/skip_tls precedence versus the overview is a separate Controller-owned seam to examine; retiring the legacy representation must not silently resolve that independent issue.

Existing Common config test bodies deliberately assert legacy fallback, legacy-present omission classification, legacy-shaped explicit plaintext and mTLS, and legacy-only JSON forms. These must become canonical contract coverage rather than be deleted wholesale. Existing Controller plaintext-gate tests and federation refusal tests, Gateway lazy-client security tests and the installed-expiry integration fixture also use the legacy field; preserve their behavioral subjects while rewriting configuration construction. Tests already covering default capacity, per-kind overrides, multi-cert selector errors, Controller-only rotation parsing, numeric rotation bounds, omitted transport and bare auto_ca remain necessary. None was executed during this review.

For future verification, establish that single and multiple certs selection, missing/duplicate selectors, empty paths and explicit skip_tls retain their intended behavior; a selector with no certs must not select hidden legacy material. Check the shipped executable defaults and generated integration blocks through the real config loaders, and exercise the existing security/installed-expiry/federation tests with canonical entries. Scope the rewrite to this shared field and its exact current consumers and documentation; unrelated EtcdTlsConfig.tls, ordinary listener/backend TLS, other Secret schemas and external Center/MCP/A2A/DNS-01 work are excluded. The byte-payload codec, protobuf protocol, ring-buffer capacities, request BodyStorage and proxy response-streaming policies are unchanged.

The alternative is to keep legacy fallback and patch its selector special case. That would correct the ghost-selector witness while retaining two serialized representations, fixture families and misleading defaults despite the explicit current contract. Removing the obsolete owner addresses the cause and leaves the existing canonical mechanism in place. The expected value is fewer security-selection branches and one auditable representation shared by both binaries and the retained federation client; this is cold-path maintainability debt, with no measured request-performance or security-impact claim. Suggested classification: architecture-debt, P3. Source-complete primary review and static supporting inspection only; no code changes, builds, tests or runtime experiments were performed.
