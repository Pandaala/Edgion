# Require a Gateway no-route outcome in the kind-denial probe

`AllowedRoutesKindsTestSuite::test_grpc_route_denied` treats failure to connect its tonic client as successful kind rejection. Once connected, it accepts every RPC error: Unimplemented, NotFound and Unavailable pass explicitly, and the final else branch passes every other non-OK status. Its outcome therefore proves only that SayHello did not complete successfully, not that allowedRoutes.kinds excluded the GRPCRoute.

The actual fixture has an HTTP listener restricted to HTTPRoute, a legal HTTP /health route, and a same-namespace GRPCRoute targeting test-grpc:30021 with authority kinds-grpc.example.com. The real TestServiceImpl::say_hello producer normally returns an OK HelloResponse. Two permitted source-level false-positive witnesses are a transient connection failure after the preceding HTTP health case, and a regression admitting the GRPCRoute while its gRPC backend is unavailable. The first returns directly through the successful connect-error branch; the second produces an RPC transport/upstream failure that the blanket status branches accept. The preceding successful HTTP request is meaningful listener evidence, but it neither ensures the later connection succeeds nor establishes the gRPC backend/protocol path is healthy. These are distinguishing failure schedules, not observed incidents or executed regressions.

The production policy owner supplies a narrower contract. Controller route_utils::listener_supports_route_kind applies the protocol matrix and optional allowedRoutes.kinds; validate_parent_ref_accepted records NotAllowedByListeners when no otherwise eligible listener admits the kind. GRPCRouteHandler writes the selected parent's Accepted condition, and the Gateway cold compiler filters accepted parent references before producing route units. The native request filter returns a trailers-only HTTP200/application-grpc response with grpc-status12 for a pure gRPC no-match when the current listener's native table has routes. With no native routes it falls through to the HTTP route lookup, whose miss calls end_response_404. That helper is gRPC-aware: for this native request it emits HTTP200/application-grpc with grpc-status5 (NOT_FOUND), rather than a literal HTTP404 response. A connection failure is not either routing decision. Unavailable, Cancelled, Internal or another arbitrary RPC failure does not prove it either.

Make this existing negative case fail when client construction, channel connection, deadline or unrelated RPC processing fails. Require a response from the intended listener with the actual supported no-route representation. For the committed kind-restricted fixture with an empty native table, expect the native NOT_FOUND/5 response from the HTTP lookup fallback; if a supported fixture intentionally publishes other native routes on that listener, its native-table no-match uses UNIMPLEMENTED/12. Do not accept both codes indiscriminately or treat a literal HTTP404 as the expected native response. Preserve tonic's correct trailer handling; if its status abstraction does not establish the required wire evidence, inspect the few HTTP/2 response fields through the harness's existing RawH2Conn and protobuf request encoding, rather than accepting every status or matching arbitrary Display text. Send the same SayHello request, require HTTP200/application-grpc and the selected canonical grpc-status, and fail on connection, stream, parse or completion errors under the existing deadline. Keep the response inspection bounded and clean up the connection driver on success, failure and cancellation. A bounded healthy H2/backend control and the exact current parent Accepted=False/NotAllowedByListeners condition can strengthen the policy attribution, but neither generic status nor a stale/foreign parent condition replaces the wire rejection assertion. Any added status read must select the declared parent and owning controller with current observed generation and fail on read/parse errors.

Keep both original case identities, the positive HTTP route, logical authority, actual SayHello request, shared topology and thirty-second owning TestCase deadline. Do not broaden the Gateway policy, alter its HTTP/gRPC no-route behavior, introduce a generic negative-test framework, reset metrics, add tracing or new traffic observability, change TLS support, or add another topology. The existing positive gRPC basic case already treats connection and RPC failures as failures; reuse its outcome discipline without consolidating legitimate suite syntax.

A positive-only control is insufficient because the listener can fail between cases and an admitted backend can fail independently. Merely removing Unavailable from the first accepted set is also insufficient: the final else branch still accepts every error. Requiring only Controller Accepted=False is an alternative control-plane check, but would discard this case's data-plane assertion and does not certify delivery or rejection at the Gateway. The bounded improvement is owning this case's negative protocol outcome precisely.

The original route-listener-protocol-acceptance-parity decision establishes the kind-admission boundary and its NotAllowedByListeners reason. The original testing discrimination rule supports distinguishing the claimed boundary rather than any unsuccessful call. ARCH283 owns TLS client preparation/handshake rejection, while the unpromoted PART447 TCP deny helper has separate transport evidence; neither is a verified finding for this gRPC owner. Numeric listener ownership is separately reported as scoped ARCH296 supplemental evidence and is not part of this outcome correction.

Future focused checks should require failure on channel refusal, channel timeout, Unavailable caused by an admitted but unreachable backend, and unrelated application errors; require success for the fixture's genuine Gateway no-route response; and require failure for a successful HelloResponse after removing the kind restriction. Preserve positive listener/backend controls and exact case identities. No tests, builds, network operations, repository mutations or performance measurements were performed.
