# Assert the header markers already sent by the BackendTLS echo cases

`BackendTlsTestSuite::test_backend_tls_echo` and `test_backend_mtls_echo` in `edgion-tests/src/client/suites/gateway/tls/backend_tls/backend_tls.rs` send ordinary `X-Test-Header` markers with values `backend-tls-test` and `backend-mtls-test`. The former explicitly says this verifies forwarding. Both accept a response solely on successful HTTP status plus the expected `Server` and `Path` strings. Neither inspects the marker it sent. A response from the correct TLS backend and path with that header absent or changed therefore passes the current forwarding assertion. This is an assertion gap derived from source, not a claimed TLS bypass, production incident or failure of the suite's existing handshake/path coverage.

The observed value is already available through the actual producer. The BackendTLS fixtures route `/backend-tls/` to port30051 and `/backend-mtls/` to the client-authenticated port30052. Both real HTTPS backend servers use `create_echo_router`; these prefixed paths reach `catch_all_handler`. That handler returns the server identity, observed client socket, method, path and a `Headers` section containing the request's header names and values. The existing display-name function renders the marker as `X-Test-Header`. No extra server API, capture state or production observability is needed. The local and Kubernetes fixtures retain the same paths and authorities, and the actual suite registration selects the canonical BackendTLS HTTP listener.

Strengthen these two existing positive cases by requiring their already-sent ordinary marker to appear with its exact expected value in the existing backend echo. Interpret header names case-insensitively and compare the value as a header-field value, rather than accepting an unrelated substring somewhere in the response. Keep the current success status, correct server and correct path checks; a marker alone must not replace proof that the intended backend handled the request. Missing or changed markers, body-read failure and transport failure must fail.

The neighboring `backend_tls_headers` case also claims header forwarding without checking a header, but its supplied `X-Trace-ID` is a managed identity input. Current `RequestTraceId::initialize` obtains the canonical W3C trace identity and publishes its standard `x-trace-id`, and later reconciliation owns upstream and response identity. Requiring the literal `backend-tls-trace-123` to survive would conflict with that boundary. Preserve this case's current input and identity behavior; any additional identity assertion should compare the actual canonical identity consistently across response and backend echo, not assume transparent forwarding of a reserved header. The decisive correction proposed here uses the two ordinary marker headers whose expected values are already explicit.

Preserve all six case identities, TLS and mTLS trust/identity settings, port and Host selection, error handling, and the pool-isolation case's independent socket-reuse, rotation, rejection, recovery and cleanup assertions. Do not change production header reconciliation, weaken certificate validation, add a generic header-test framework, alter fixture topology, replace tests with mock-driven production seams or add logs/metrics. The existing echoed header section is the narrow evidence owner.

An alternative is to remove the unused marker inputs and describe these cases only as TLS/path success checks. That would make the descriptions more honest but discard the explicitly intended ordinary-header forwarding regression. Reading existing output is the bounded improvement. Its value is precise evidence for a small existing promise; priorityP3 reflects this limited test gap, and there is no performance claim. The absence of marker checks does not invalidate the separate status/backend/path assertions.

Future verification should retain successful existing TLS and mTLS echo responses, reject otherwise identical responses with the marker missing or changed, accept legitimate header-name casing, and demonstrate that canonical `X-Trace-ID` processing remains unchanged. Read original integration assertion guidance, upstream TLS/client-identity and pooling decisions, actual fixture and backend producers, canonical request identity initialization and real pool test bodies. Current findings/tasks were searched; no existing ordinary BackendTLS marker-assertion correction was found. ARCH352 concerns additional SAN rejection attribution and is outside this cause. All evidence is static repository source; no tests, applications, builds or network calls ran.
