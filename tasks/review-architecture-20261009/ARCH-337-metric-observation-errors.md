# Preserve metric observation failures before computing policy deltas

`edgion-tests/src/client/suites/edgion_backend_traffic_policy/retry_budget.rs::denied_total` and `upstream_authority.rs::rejected_total` both return an unconditional `f64`. They convert a failed `MetricsClient::fetch_raw_metrics` call to `0.0` and similarly replace a selected nonnumeric sample with zero. Their callers cannot distinguish a successfully observed absent series from a failed baseline observation. They then subtract or compare that synthetic baseline with a later successful lifetime-counter read and may accept old counter history as new policy evidence.

`test_budget_denies_under_load` samples the existing bare `edgion_gateway_retry_budget_denied_total` before sixty concurrent requests and requires an afterward delta of at least eight. The actual `/status/503` producer returns 503 independently of budget admission, so all sixty final 503 responses do not distinguish admitted retries from refused retries. Consider a prior invocation leaving a count of at least eight, one failed baseline scrape, and a subsequent invocation whose requests produce no new budget denials while the afterward scrape recovers. The local helper supplies before=0; the retained count becomes delta>=8 and the case can pass. A prior successful run on the same live Gateway followed by direct re-invocation is sufficient history; no metric reset, impossible counter value or fabricated production corruption is required.

The authority suite has the same observation-result defect. `test_fail_closed_render_empty` and `test_injection_rejected` sample reason-specific rejection totals before traffic, then require increases. A failed baseline becomes zero; an old render_empty count or two old invalid_label counts can satisfy the respective metric assertion when a later scrape recovers. These tests also require 502 responses, which remains valuable functional evidence, but that status alone does not establish that the named authority reason emitted its required new counter observations. This finding does not claim that an authority bypass returning 200 would pass.

The common client already preserves errors. `MetricsClient::fetch_raw_metrics` returns Result, checks HTTP success and propagates transport/body errors; these two suite-local adapters discard that distinction. Existing emitters increment cumulative counters, and the authority emitter uses fixed reason labels. The legitimate missing-series convention is independent: on a successful valid scrape, a counter or reason that has never been registered may represent zero.

Return a fallible observation from the two narrow counter readers and require a valid baseline before generating measured traffic. Propagate failed before/after scrapes and malformed selected samples to TestResult with safe operation/metric context. Preserve successful absent-series zero. Validate the exact metric name and existing reason identity, finite nonnegative counter samples, and nondecreasing before/after observations; reject a reset instead of accepting an undefined delta. Use the existing MetricsClient endpoint selection, authentication/transport contract and deadlines. A small harness-local counter-reading function is appropriate if these callers genuinely share it; do not widen all existing metric analyzers or introduce a generic metrics framework. The current permissive `counter_value` helper is not a complete replacement because it filters parse failures and also returns an unconditional sum.

Keep the current sixty-request concurrency, all request/join/status failures, the soft retry-cap band, minimum-rate floor case, native upstream 503 producer, authority rejection status/reason cases and fixture identities. Preserve absent-series behavior for freshly started Gateways without pre-registering metrics. Add no product counter, new label, global reset, request observability, retry-policy change or replacement topology. This recommendation makes the evidence boundary truthful; it does not make these unlabeled/global counters per-request attribution or prove the exact number of admitted retries.

ARCH280 concerns suites lacking a measured before/after traffic window. These callers already have such a window but erase the failure to obtain it, requiring a different correction at observation-result ownership. ARCH281 concerns complete retry-attempt evidence for the LeastConn storm, not these metric adapters. Original integration delta and test-discrimination decisions support trustworthy current observations, while historical retry-budget integration passes do not establish behavior during a failed scrape.

Future focused tests should keep a prior count unchanged across a failed baseline and a recovered afterward observation and require failure; cover failed afterward reads, successful missing series, malformed/nonfinite samples, counter decreases, and valid current increases. Keep actual authority and retry-budget algorithm regressions. No test, build, network operation, repository mutation or performance measurement occurred.
