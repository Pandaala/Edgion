# ARCH-348: Negative response-body assertions must fail on unreadable observations

## Claim and current ownership

Two registered Canary anti-spoof cases, CredentialInjector's shared fail-closed assertion, six ExtProc cases, ForwardAuth's strict-status case and HmacAuth's hide-credentials case convert response-body read failures into successful evidence of absence or successful path discrimination. The common cause is loss of the observation result: `response.text().await.unwrap_or_default()` substitutes an empty string, and the following negative predicate accepts it. HTTP status checks remain valuable but do not prove that the body was successfully observed.

`spoofed_dye_header_stripped_on_fallback` in `edgion-tests/src/client/suites/edgion_plugins/canary/canary.rs:220–257` and `spoofed_dye_header_stripped_when_kill_switched` at `:565–604` send a forged `X-Canary-Active` header to `/echo`, require HTTP 200, then default a failed body read at lines 241 and 586. An empty substituted body contains no `x-canary-active`, so both cases can return PASS without observing the backend's headers. The shared client has a five-second request timeout and these cases retain the thirty-second wrapper deadline; an earlier body-read error can reach the PASS branch before the wrapper expires. This is a conditional false-PASS path, not evidence that Gateway stripping is currently broken or that the authored echo normally fails.

The real echo handler emits server, method, path and header lines. Relevant local and Kubernetes fixtures bind both cases to the stable backend on port 30001 and declare the request dye name, including the internally kill-switched Canary entry. Current client and runner registrations include the static Canary suite. The expected completed echo is therefore available as positive observation evidence before testing header absence.

`assert_fail_closed` in `edgion-tests/src/client/suites/edgion_plugins/credential_injector/credential_injector.rs:293–329` requires HTTP 500, then defaults a failed body read at line 304. Its lowercase absence check rejects the four authored markers `client-spoof`, `bearertoken`, `credentialinjector` and `credential_injector`; an empty substituted string passes all four checks. The static `missing_secret_fails_closed` case and the dynamic `credential_injector_dynamic_deleted` case both call this helper. The dynamic scenario's deleted-phase factory actually selects that suite, and both topology fixture sets provide the referenced Secret/plugin/route and deletion target. These are two live uses of the same helper, not two separate cleanup or generation findings.

A successful complete empty error body is legitimate. The original fail-closed body contract explicitly permits `body: None`, and actual CredentialInjector rejection code and existing unit bodies retain empty-body 500 outcomes. The defect is accepting a failed read as if it were that successfully completed empty body. It does not establish credential disclosure, failure of the current production empty-body path, or a whole-suite false pass. The existing marker list is preserved; this finding does not claim it proves every possible secret or internal detail is absent.

The pending REPORT-PART-476 ExtProc supplement exposes the same result loss in six registered fast-tier cases. `processor_closes_before_request_verdict` and `processor_closes_before_response_verdict` default reads at lines 1849 and 1890; `fail_close_returns_500`, `bad_verdict_fail_closes` and `streamed_degenerate_continue_and_replace_fail_closes` do so at lines 3040, 3116 and 3330. All five require HTTP 500 and use `is_sanitized_fail_close_body`, whose accepted generic shapes include an empty body. A failed read therefore passes its generic-body and prohibited-detail checks. Actual `ExtProc::fail_mode` returns `ErrResponse { status: 500, body: None }` on fail-close, so successfully completed empty 500 responses must remain accepted. Existing fail-mode unit bodies protect the fail-open/fail-close outcome distinction; they do not observe an integration response body's completion.

ExtProc's sixth case, `fail_open_passes` at lines 3052–3087, requires HTTP 200 for GET `/get`, defaults the body read at line 3071, then passes whenever `x-ext-proc-req` is absent. The local and Kubernetes dead-target fail-open fixtures route to the existing port-30001 backend. Its catch-all handler serves `/get` with server, method, path and header lines. An unreadable, empty or unrelated 200 cannot establish that this backend received the bypassed request. The separate `streamed_fail_open_passes_original_body` case requires the positive `untouched-payload` marker and does not pass on a substituted empty string; it is not an additional false-PASS site in this extension.

The pending REPORT-PART-480 ForwardAuth supplement is `success_excludes_200_treats_as_failure` at lines 1445–1512. Both topology fixtures set `success.statusCodes: [204]` while the request uses `Bearer valid-token`. The real auth producer returns HTTP 200 JSON with `status: "ok"` and `user: "test-user"`; the ordinary backend `/health` returns plain `OK`. Production classification intentionally rejects the auth 200 under this configured status list and relays that response. The case defaults a failed body read at line 1469, then its alternate `status == 200 && !backend_body` branch accepts the empty substitution, or any unrelated completed 200 that lacks its backend markers. A status of 200 alone cannot distinguish these two paths. This is an observation defect, not a production success-classification defect or a reason to reject legitimate empty 204 auth responses in the separate custom-status case.

The pending REPORT-PART-491 HmacAuth supplement is `hide_credentials_removes_auth_header` at lines 177–225. It sends a valid signed GET `/headers`, requires HTTP 200, defaults the body read and passes when the lowercased string lacks `authorization`. Both topology fixtures enable `hideCredentials`; actual HmacAuth success removes the configured credential headers before forwarding. The real `/headers` producer returns a JSON object with an object-valued `headers` field. A read error or unrelated empty 200 provides no evidence about those upstream headers. This does not establish that current production stripping fails or that any credential was disclosed.

## Bounded improvement and alternatives

Keep observation ownership in the existing cases and the CredentialInjector helper. Make each scoped body read fallible and return a failed TestResult with a value-free operation diagnostic on error. Do not print body contents, credential values or raw dependency errors merely to explain failed observation. No shared-client, transport, runtime registry or production abstraction is needed.

For Canary, require the successfully completed body to identify the existing fixture echo before checking header absence: use the existing server-port extraction with expected port 30001 and the actual GET `/echo` and header-section markers. Preserve the forged-header assertion. A completed empty or unrelated HTTP 200 body is not evidence that the intended backend saw the stripped request. Two explicit reads and checks suffice; a small case-local predicate is optional if it reduces actual duplication without becoming an echo framework.

For CredentialInjector, retain expected HTTP 500 and inspect only a successfully read complete body for the existing four prohibited markers. Accept `Ok("")`; require neither an echo shape nor a nonempty error message. Preserve the static missing-Secret and dynamic deleted-Secret identities, requests, spoofed input, lifecycle/status barriers, fixture selection and existing deadlines. The nearby `assert_upstream_header` and Connection-nomination request helper already propagate body-read errors and supply a bounded local precedent; do not rewrite their separate positive-header, capture, diagnostic or cleanup contracts.

For the five ExtProc sanitized-500 cases, keep HTTP 500 and the complete existing generic-body/prohibited-detail predicate, but apply it only after a successful complete read. Accept `Ok("")`; require no echo shape or nonempty error message. For `fail_open_passes`, keep HTTP 200 and the existing processor-header absence assertion, but first require a successfully completed fixture echo identifying port 30001, GET `/get` and its header section. Preserve the fake-processor modes, dead target, configured failure policy, request/response phase distinction, streamed degenerate case and fast/full tier placement.

For ForwardAuth's strict-status case, remove the loose alternate PASS branch. Require a successful complete read and parsed authored auth JSON with `status == "ok"` and `user == "test-user"`, in addition to the existing HTTP 200 and backend-exclusion assertion. Unreadable, empty, malformed or unrelated bodies fail. Preserve the valid token input, `/health` request, strict `[204]` configuration and the separate custom-204 case; do not change denial relay, configured client headers or production status/body classification.

For HmacAuth, require a successful complete read and the actual `/headers` JSON shape with an object-valued `headers` member before applying the existing authorization-absence assertion. Missing or invalid shapes fail rather than becoming an empty header map. Preserve the existing negative marker check, valid signing helper, method/path/Host/date/signature inputs, HTTP 200, hide-credentials configuration and all other authentication cases. Do not emit the echoed headers, signature, body or credential material in new observation-error diagnostics.

Keeping defaulting is shorter but conflates failed observation with verified absence. Pure stripping and credential unit tests cannot replace the end-to-end response observations. A general response/assertion framework adds no necessary value for these case-local read sites.

## Preserved contracts and future verification

The runtime installs and strips the dye plan before plugin invocation, conditions and Canary's internal kill switch. Original dye-stage knowledge and existing unit bodies preserve once-per-name stripping, case-insensitive names, missing plans and response-only rules. Entry disable and Canary's internal kill switch remain distinct. Do not change that owner, selection/fallback policy, dye generation/rendering, deferred credential injection, mirrors, canonical access logs, body storage or response streaming.

Preserve both Canary hosts and HTTP 200 expectations, stable-backend routing, local and Kubernetes registrations, the CredentialInjector 500 contract and dynamic phase order, and all live test identities/assertions. Retain canonical binary-owned logging, redaction and observability restraint, existing metrics, BoringSSL and product/workqueue boundaries. These are test-observation corrections and need no production semantic change.

Future focused verification should require a body-read error after Canary HTTP 200 or CredentialInjector HTTP 500 to fail. For Canary, the expected complete echo containing the forged header must fail, the expected complete echo without it must pass, and empty/unrelated bodies must fail. For CredentialInjector, a successfully completed empty body and a completed generic body without the existing prohibited markers must pass, while each prohibited marker must still fail. Exercise both static missing-Secret and dynamic deleted-Secret callers without weakening their current lifecycle checks, and retain local/Kubernetes execution coverage.

Future focused verification for the accepted extensions must require read failures after their expected statuses to fail. Each ExtProc sanitized-500 predicate must still accept a successfully completed empty body and reject its existing prohibited details. The fail-open predicate must pass only on the intended complete `/get` echo without the processor header. ForwardAuth must pass the authored auth JSON and fail plain backend `OK`, unrelated JSON and empty/unreadable 200 bodies. HmacAuth must fail unreadable, empty, malformed or missing-headers observations; valid fixture-shaped observations must retain the existing authorization-presence rejection. Keep all current identities, requests, fixtures, assertions and deadlines, without a new production metric, log or response-body owner.
