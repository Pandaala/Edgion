# Wait for both prepared policies before asserting oldest-wins

`edgion-tests/src/client/suites/edgion_backend_traffic_policy/control_plane.rs::test_conflict_oldest_wins_and_promotion` submits the newer LeastConn policy and then calls `poll_lb` with the already satisfied predicate `Ewma`. `poll_lb` returns on its first matching read, before its sleep. That read can still describe the generation containing only the earlier Ewma policy. The test then deletes the earlier policy and checks LeastConn promotion, without ever proving that the two intended policies coexisted in a prepared Gateway generation while Ewma was the selected winner.

The failure witness is a latest-wins regression in Gateway arbitration. Apply the older Ewma policy and observe it. Persist the newer LeastConn policy; before its asynchronous delivery or prepared publication, read the still-current Ewma map and accept it. Delete the older policy. Once the newer policy is processed, or its add is coalesced with the removal, observe LeastConn and accept promotion. All named assertions can pass although the Gateway would have selected the newer policy while both were present. This is a permitted source-level scheduling witness, not an executed regression or deployment incident.

The real ingress does not provide a runtime acknowledgement. `TestContext::apply_yaml` returns on successful Controller Admin PUT/POST. The namespaced EBTP branch awaits the backend writer, and the FileSystem writer returns after persistence. The Gateway separately receives conf_sync events. `CacheData::set_conf_processor` waits for notification and a 100 ms `BATCH_DEBOUNCE` before `process_compressed_events` invokes the synchronous handler. Watched resources may already exist in the generic configclient cache during that delay. Therefore waiting only for `/configclient/edgionbackendtrafficpolicy/list` to contain the loser is a stronger ingress observation but still not proof of prepared arbitration.

The canonical runtime already has the right owner. `BackendTrafficPolicySnapshot` contains its generation, prepared typed candidate index and effective policies together. `prepare_policy` admits valid resolved Service candidates independently of their Controller conflict status; `publish_generation` chooses the first prepared candidate and publishes one immutable snapshot. `lb_policy_snapshot` currently exposes only the effective algorithm through the existing debug store-stats response. Its omission of prepared membership is what makes the unchanged Ewma value insufficient evidence for this particular transition.

Bind the conflict assertion to one prepared runtime observation that contains both current intended Service policies and the expected older winner. Use a small metadata-only projection from the existing immutable BackendTrafficPolicySnapshot through the existing authenticated integration/debug surface: typed target, bounded candidate identities/current generation identity and effective winning policy/algorithm are sufficient. Take all correlated facts from the same snapshot, and preserve existing access restrictions. Poll this combined condition under the existing case deadline before deleting the winner. Then require the newer intended policy to be effective after removal, with the removed winner absent from the corresponding prepared candidate observation. Missing, malformed or timed-out evidence fails. Avoid reporting success merely because an unchanged algorithm, a generic cache entry or a Controller status already satisfies the predicate.

Keep the oldest creation-time/name tie-break contract and the deliberate `a-win`/`z-lose` fixture names, real Admin writes, typed Service ownership, asynchronous conf_sync compression and current promotion assertion. Do not add a request-path allocation, policy registry, logging/metric family, handler acknowledgement channel, arbitrary stabilization sleep or second topology. This is bounded management/test evidence, not new request observability. A target-scoped projection is preferable to exposing all policy specs or copying Secret-bearing resources; canonical candidate preparation remains the production owner.

An alternative is a deterministic transport-level integration driver that holds delivery until both policy updates reach the existing handler and then inspects one runtime snapshot. That requires more harness wiring. Controller conflict status alone is insufficient because Controller and Gateway arbitrate independently; repeated unchanged Ewma polls for an arbitrary duration still do not establish publication. The existing `oldest_wins_then_promotes_on_delete` unit test inserts both policies synchronously into the real store and protects algorithm semantics, but it cannot replace the live case's source-to-Gateway boundary.

Original EBTP architecture and atomic-snapshot decisions require oldest-wins and identify the single immutable prepared owner. Integration tests must discriminate their claimed boundary. ARCH055 concerns creation-time precision and remains separate; this witness survives different timestamp values and a correct lexical tie break. ARCH265's swallowed cleanup outcomes are separate supplemental evidence in this file, and correcting cleanup alone would not create the missing conflict-phase barrier. No tests, builds, network operations or repository mutations were performed.

Future focused verification should delay the loser publication, run an intentionally latest-wins selection through the same observation logic, and require failure before winner deletion. Also cover both prepared candidates with correct oldest-wins, subsequent removal/promotion, a generic cache entry awaiting handler dispatch, stale intended identities, and observation errors. Preserve the existing synchronous arbitration unit test and all live test identities.
