# ARCH-264 — Dynamic scenarios must own initial state and restoration

Several older dynamic scenarios leave their authored mutations in the shared Controller/Gateway topology after success or skip restoration when a transition fails. BasicAuthDynamic and its grouped variant, BodyDynamic, BtlspRefFlap and CanaryHotSwap also assume that runner preload established the initial generation. ConditionRefsDynamic already applies and waits for its initial generation, but its restoration still runs only after every transition succeeds. These missing completion paths can leave state for a later invocation or suite.

The affected owners are edgion-tests/src/client/dynamic/scenarios/basic_auth_dynamic.rs:29-37,68-76; body_dynamic.rs:44-56; btlsp_ref_flap.rs:43-53; canary_hot_swap.rs:35-43; and condition_refs_dynamic.rs:34-49. They share one root cause: restoration is absent or appears only as an ordinary final state-machine step rather than a scenario-owned completion path that runs after either transition outcome.

BasicAuthDynamic and its grouped variant assert the initial phase, remove bob's Secret/group reference, and return success without restoring it. The actual initial suites require bob=200 and update suites require bob=401. The phase manifests name the same EdgionPlugins keys. A second direct invocation against the same successfully updated topology therefore fails the unchanged initial business assertion. CanaryHotSwap similarly leaves its Selector active=canary and modified dye generation, while its initial suite requires the stable backend at port 30001. BodyDynamic ends after publishing an invalid plugin generation; its last-known-good transport body is the restored/updated value rather than the initial value. Its capped transition also temporarily writes the shared example-gateway request-body policy, so a failure before the to_restored step can leave the 16B cap active. ConditionRefsDynamic restores its Secret only after all rotation/delete assertions succeed; BtlspRefFlap restores ca-good only after its invalid-phase assertion succeeds. Neither reaches that restoration after an earlier error.

This is a supported invocation boundary, not a conjectured incident. test_client.rs::run_dynamic_scenario directly invokes the selected scenario without resetting fixtures. The local loader excludes DynamicTest/updates and delete directories and preloads initial generations at startup. On the full --with-reload path, run_integration.sh invokes run_all_tests before and after reload, and both full sweeps include dynamic enumeration. Between those sweeps it requests the Controller reload and checks server IDs, rather than applying original fixtures again. FileSystemStorage::update_one_if_version merges the operator update and writes the existing file atomically, so a reload does not undo authored mutations. This review did not execute a sweep and does not claim that every existing full run has reached these witnesses without another earlier failure.

Make each affected scenario establish its declared initial state using the existing apply helpers, then wait for its original initial business phase. Capture initial setup and all transitions in one result, and attempt restoration outside that result before returning. Attempt every owned restoration operation even if another restoration fails, then verify the original business behavior where the reset operations succeeded. For BodyDynamic, restore both the shared request-body policy and the original plugin generation, including when the capped or rejected transition fails. Restore Canary's Selector and changed plugin dye together. Restore the condition Secret and BackendTLSPolicy source after failed assertions as well as success. Use the existing apply/wait ownership and preserve all current phase assertions, transition order and invalid-generation checks. Propagate restoration failure; when transition and restoration both fail, retain both operation contexts without exposing Secret bodies. The existing AllowedSanRegexIgnoreCase and AllEndpointStatusTls result/cleanup composition provide actual local patterns. No generic scenario runner, cleanup registry, sleep-based readiness or product-runtime change is required.

The Kubernetes wrapper already restores declared reset fixtures before and after scenario execution, and the observed gap is not a claim that that wrapper omits cleanup. Keep its run-scoped ownership, status/endpoint barriers and failure reporting. Scenario-owned restoration also protects documented direct invocations and local shared/reload sweeps. Reloading all fixtures between sweeps is a weaker alternative: it does not repair a direct repeat or ensure cleanup after a failed transition, and it broadens mutation beyond the scenario's owned keys.

Original dynamic testing and tracked-Secret knowledge explicitly require establishing initial state and restoration on success and failure. Accepted local single-owner takeover does not permit leaving configuration mutations for later suites; Kubernetes cleanup remains independently scoped. Existing phase suites and fixtures were read, not executed. Future verification should exercise two consecutive real scenario invocations and an injected failure after each mutation, check that original traffic/status/body behavior returns, and ensure cleanup errors fail the scenario. Retain current assertions rather than replacing them with apply success or static fixture comparison. No test, build, network operation or repository mutation occurred.
