# Bind metric assertions to the traffic produced by the current case and phase

Four active LB suites and the BandwidthLimit metrics case judge current behavior using lifetime counter aggregates. The missing owner is a measured traffic window: successful current requests and their exact metric increments are not bound together before the behavior verdict. Earlier traffic can therefore satisfy an assertion about a failed or pinned current case.

## Current call chain and falsifiable witnesses

`lb_consistenthash.rs` runs five real header, cookie, query, multi-slice and source-IP cases. Each joins generated tasks with `let _ = task.await`, ignoring join errors, HTTP errors and response statuses, then calls `MetricsClient::analyze_chash_consistency("lb-ch-test")` after a fixed sleep. A nonzero aggregate and `is_consistent` produce success. The first three cases generate twelve requests; multi-slice generates fifteen and source-IP twelve. The shared Gateway fixture gives all these routes the same test key. No baseline, current per-key count, expected backend Service or endpoint authority controls the verdict. Prior consistent header traffic followed by a cookie case whose requests all fail before recording new metrics leaves the prior keyed aggregate nonzero and consistent; the cookie case can pass without a successful cookie request. This is a permitted static witness, not an executed failure.

`lb_ewma.rs` and `lb_leastconn.rs` correctly reject request/join/status failures for their twelve concurrent requests, but their distribution checks require only nonzero lifetime totals and at least two observed endpoints. Prior traffic on endpoints A and B followed by twelve successful current requests pinned to A still leaves two endpoint series and passes. These adaptive suites do not promise exact equal distribution; diagnostic variance is not itself a required assertion.

`lb_leastconn_retry_on_status.rs` correctly requires eight final 503 responses and eight successful healthy responses. However its purported healthy-phase endpoint check consumes lifetime `analyze_lb_distribution("lb-lc-rs")` only after both phases. The current retry storm itself can populate A and B, while all subsequent healthy traffic goes to A. The check still sees two endpoints without any previous run. This is the same missing measured-window cause at an intra-case phase boundary.

`BandwidthLimitTestSuite::test_metrics_verification` in `bandwidth_limit/bandwidth_limit.rs` sends a 51,200-byte POST but checks neither its HTTP status nor the result of reading its response body. Sending errors and metric-fetch errors already fail. After a fixed 500 ms sleep, it fetches all backend metrics, keeps every series containing `latency_ms` and passes when their lifetime maximum is at least 800 ms. The generated `_test_key` is unused, and the claimed route filter is absent. Its immediately preceding functional-compliance case can leave a qualifying slow sample; a later completed HTTP error or failed body read can then pass this metrics verdict using the prior sample. The case need not even observe a fresh attributed increment. This is a static accepted-outcome witness, not an executed failure or proof that the entire suite passes.

Both local and Kubernetes BandwidthLimit fixture sets configure the same compliance, metrics and selected-BackendRef cases against `test-http`, with rates of 100 KiB/s, 50 KiB/s and 100 KiB/s respectively. Their shared `edgion-plugins-gateway` carries the actual `metrics-test-type: latency` annotation. The similarly named annotation on the metrics plugin resource is not the enabling owner. The published listener projection and terminal logging read the Gateway annotation, and test-mode latency measures elapsed time from `upstream_start_time` until terminal recording. Compliance traffic can therefore contribute the prior sample. The plugin remains deliberately stateless and per response stream; transport, backend work and scheduling also contribute to elapsed time, so this observation is not isolated throughput evidence.

The helper's public aggregate methods intentionally analyze the supplied cumulative series. They are not defective simply because they return lifetime totals. `pg_logging::record_request_metrics` records the existing backend counter at terminal logging; test-mode LB data contains final endpoint and hash key, and `record_backend_request` increments it without a per-case reset. Cases run serially through `TestSuite::run`; neither ordinary registration nor an independent test invocation resets the counters between these observations. Counter emission is restricted to the existing integration opt-in contract.

## Bounded improvement and invariants

Take an existing backend metric snapshot immediately before each measured request group and compare it with a snapshot after that group's successful exchanges finish. For the LeastConn retry case, the healthy baseline belongs after the storm and before the healthy group. Reject failed requests, joins, unexpected status/body completion, counter decreases/resets, missing increments and unexpected attributed traffic before evaluating the policy. Keep the exact twelve/fifteen/eight successful-client-request counts; these terminal backend counters are client-exchange observations, not retry-attempt counts.

Use authoritative committed EndpointSlices locally and the existing Kubernetes endpoint-inventory mechanism for cluster fixtures. Verify recorded positive deltas belong to the intended backend Service and allowed endpoints; require complete attribution. Retain the adaptive suites' existing at-least-two-endpoint condition on positive current deltas rather than importing strict RoundRobin equality or requiring every eligible adaptive endpoint receive a request. For each consistent-hash case, require the complete intended key/request set in the delta and exactly one allowed endpoint for each key. A five-key, four-endpoint multi-slice fixture does not by itself guarantee every endpoint is selected; do not invent that distribution requirement. Source-IP key identity needs its actual client-address authority rather than a hardcoded loopback assumption in Kubernetes.

For the BandwidthLimit metrics case, take the baseline before its POST, require the expected successful status and a successfully completed response of the expected payload size, then poll under the existing deadline for exactly one new attributed terminal backend increment. Evaluate the existing 800 ms latency threshold only on positive count deltas from that window. Preserve the 51,200-byte request, the compliance and BackendRef cases and their body/duration checks, all three identities/order, current fixtures and thirty-second case deadline. Use the fixture-authoritative exposed Gateway, backend Service, protocol and status identities and the complete existing test-data series identity. The current parser does not retain route labels, so a route name in an error message is not attribution. Reject ambiguous/excess traffic rather than using a global maximum; do not infer a new per-request key from the unused generated string.

Reuse the existing raw `BackendMetric` representation and the RoundRobin before/after ownership pattern. Extract only a small harness-local delta/attribution mechanism when genuinely shared; keep key and adaptive policy checks with their suites. Existing whole-life analysis APIs may remain for their legitimate consumers. Fixed sleeps can become bounded polling for the exact expected delta; expiry or excess counts must fail. Do not reset global metrics, add a new product metric/high-cardinality label, reconstruct expected endpoints from observed metrics, or add a generic test runtime framework.

Preserve case names/order, existing concurrency needed by adaptive selectors, traces, fixture/policy semantics, retry budgets, lifecycle/report failures and live tests. No production selector, access-log, TLS, body or workqueue change is needed. The existing strict RoundRobin suite rejects missing/unbalanced/unexpected traffic, wrong Service, counter decreases and topology errors. Its five unit test bodies cover exact deltas, missing/unbalanced/unexpected traffic, wrong Service/unattributed totals, topology resolution and the integration metric-label configuration; they do not include a counter-reset assertion. Keep its sequential equality contract intact.

## Knowledge and verification limits

The original `integration-lb-metrics-require-scoped-deltas.md` explicitly rejects stale nonzero totals and observed endpoint counts without scoped evidence. Its historical RoundRobin resolution does not prove these other callers comply. Current registrations, all nine PART555 implementations and embedded tests, actual local fixtures, metric producer/parser/analyzer and relevant LB unit bodies were inspected. The PART460 supplement adds the independently inspected BandwidthLimit implementation, all three case bodies, both complete fixture sets, Gateway annotation publication and terminal latency producer to this same measured-window cause. The original per-stream bandwidth and no-runtime-tracing decisions remain intact. No matching separate candidate was found in the recorded finding titles or original testing topic searches; ARCH252 concerns an orphan file-log API, not these live metric assertions.

Future verification should drive the real decision helpers with unchanged prior consistent traffic and zero current keyed traffic; prior A/B plus current A-only deltas; storm A/B plus healthy A-only deltas; missing keys/counts, unexpected Service/endpoint, reset and transport/join/status failures. Bandwidth verification must additionally reject a prior slow sample followed by a current HTTP error, body-read failure, missing increment or fresh below-threshold latency, while accepting a complete successful response with its own qualifying attributed increment. Valid fresh hash/adaptive/bandwidth windows must pass under supported topology. This review did not run tests/builds, modify sources, reproduce a CI incident or establish measured performance. The separate lack of observed retry-attempt evidence is recorded in ARCH281.
