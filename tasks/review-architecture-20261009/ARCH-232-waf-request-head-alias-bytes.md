# Share immutable request-head bytes across WAF collection aliases

`RequestState::build` gives each WAF transaction one owned byte arena, but populates logically aliased collections by copying the same input field into that arena repeatedly. The query path calls `push_query_collection` four times for `ARGS`, `ARGS_GET`, `ARGS_NAMES` and `ARGS_GET_NAMES` (`transaction.rs:5464–5467`). Each call rescans the query and percent-decodes the name; the two value collections also decode the value independently. A single query field therefore stores its decoded name four times and its decoded value twice. The two header collections and the two cookie collections similarly copy each source name twice (`transaction.rs:5519–5590`). This is avoidable payload duplication within an owner that already represents values by immutable `ByteRange` references.

This runs on the real request path. The Gateway WAF request filter constructs borrowed `RequestHead`/`RequestHeader` views and calls `Transaction::new_shared_with_policy` before retaining the transaction in its request context (`edgion-gateway/src/plugins/http/waf/mod.rs:360–440`). `RequestState::build` converts those temporary borrows into transaction-owned state. Ownership across later callbacks is required; independent byte copies for each collection alias are not. No request payload may remain borrowed from the transport across an await.

For example, the one field `q=hello%20world` occupies four decoded one-byte names and two decoded eleven-byte values in the request arena, apart from the separately required scalar request views. The four collection records must remain distinct, with the same selected names, values and order, but can refer to one decoded name range and one decoded value range. This is aliasing of one immutable source field, not content interning between different fields. Duplicate query fields, duplicate headers and repeated cookie names must remain separate source entries even when their bytes compare equal.

The representation already supports the bounded alternative: `push_request_path_collections` stores the decoded filename once and gives `REQUEST_BASENAME` a subrange of that same arena (`transaction.rs:5591–5624`). The same ownership pattern can serve the query aliases and the header/cookie name aliases. Keeping each logical collection in the existing collection array preserves the canonical selector and candidate-order mechanisms; it requires no registry, hash table, global cache, extra request owner or public abstraction.

The important migration boundary is accounting. `projected_derived_bytes` currently projects the repeated arena payload exactly, including query names multiplied by four, query values multiplied by two, and header/cookie names multiplied by two (`transaction.rs:5954–5996`). `RequestState::build` combines that result with collection metadata for preflight admission, then derives the retained charge from `bytes.len()` and actual `entry_count` (`transaction.rs:5439–5458,5488–5505`). Simply sharing ranges would silently reduce the established retained-byte charge and could admit requests that currently fail a logical limit. Preserve the current nominal alias charge explicitly while calculating the smaller physical arena reservation. Both values can be computed by the existing private projection walk, using the existing decoding-length helper; there is no reason to introduce a second parsing implementation. Retained accounting after construction must continue using the original alias charge plus the actual entry metadata, rather than the new compact arena length.

A bounded refactor would decode each query field once into the existing arena and emit the same four ordered alias records using its ranges. It would copy each header and cookie name once for its two collections. Keep the current input/header validation, query and cookie count admission, collection-entry admission, retained preflight and final accounting in their existing order. Preserve the original `+`-to-space query decoding, invalid-percent behavior, cookie trimming and empty-name filtering, raw query/scalar views, and path decoding where `+` remains literal. Ordinary operator, TX, capture, control and selected-value logical charges must remain unchanged.

Range sharing also touches an existing consumer: `OrdinaryScanCache` keys eligible immutable request inputs by `(ByteRange, transformation_plan)` (`transaction.rs:4746–4775`). Aliases of the same field may consequently reuse a previously valid scan. Verify that logical operator admission still occurs for each selected value and that cache reuse only changes actual physical work, as permitted by the WAF optimization contract; do not add a collection-specific cache or preserve redundant copies merely to force extra scans. Distinct nonempty source fields must retain separate byte storage rather than being content-interned. Empty fields may have equal zero-length ranges, as the current copy helpers already permit; their logical records and order must remain distinct. Do not add padding or new source-identity metadata merely to distinguish empty ranges. Mutable TX/body/response sources must keep their existing exclusion and invalidation behavior.

The concrete benefit is fewer repeated decode/copy operations and a smaller requested request-head arena for inputs with collection aliases. This is not a claim about fewer allocator calls, measured throughput, process heap, RSS or incidents. All current inputs remain independently bounded, so the priority is P3. Legitimate complexity remains in preserving SecLang collection identity and budget/error semantics, not in retaining identical immutable payload multiple times.

An alternative is to retain the current copies and loops. That is simple and bounded, but keeps the same input-to-collection decoding relationship implemented repeatedly on every request. Borrowing transport storage instead is unsuitable because transactions survive the request filter. Generic content interning is also unsuitable: it adds work/state, conflates distinct input entries and expands the change beyond source-field aliases.

Verification should compare every collection's ordered name/value outputs before and after, including duplicate query fields, repeated cookies, duplicate mixed-case headers, empty/nameless values, malformed percent escapes, percent-encoded bytes and query/path `+` differences. Existing tests `request_state_preserves_query_header_and_cookie_order` and `every_count_and_byte_limit_rejects_first_excess` (`transaction_test.rs:595–697`) cover the current ordering and admission baseline. Add exact and one-less checks around the preserved nominal retained charge and unchanged count/byte limits, including cases where multiple validations could fail, and deterministic private arena/range assertions showing that aliases share bytes while distinct source entries remain distinct. Recheck ordinary accelerated/reference outcomes, ordered actions and logical work limits when range identity permits additional scan reuse. Do not add request metrics or expand production visibility for tests.
