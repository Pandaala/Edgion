# ARCH-344 — Supply the retry-quota fixtures required by the selected Kubernetes SingleProvider suite

The Kubernetes runner selects EdgionBackend/SingleProvider and invokes the same static suite as the local runner, but its published fixture tree omits the route and plugin required by the unconditional priority_retry_business_quota case. The case therefore cannot exercise its declared failed-plus-successful-attempt charging contract in the repository-owned Kubernetes topology. This is a test-harness behavior defect, not evidence of a production quota defect or an observed live integration incident.

The primary owner is edgion-tests/src/client/suites/edgion_backend/single_provider.rs. Its priority_retry_business_quota function at 1308–1417 sends the first request to ai-retry-quota.example.com, requires a successful response, and then requires exactly two dispatched attempts: a retryable 503 with estimated input and a successful 200 with reported input/output 11/7. It reads the real business-quota Redis bucket for edgion-test/ai-proxy-priority-retry-quota/#0, checks that both attempts were charged, and requires a following request to receive local 429 without another upstream attempt. test_cases at 3089–3093 registers this case without a Kubernetes exclusion. The failed attempt must contribute more than two tokens so the successful attempt's 18 tokens alone cannot exhaust the configured 20-token quota. These assertions are meaningful and must remain.

The execution chain is present. test_client.rs:1783–1788 installs SingleProviderTestSuite for this literal selection. run_k8s_integration.sh:2627 lists EdgionBackend/SingleProvider; its classification and batch branch at 2640–2699 selects that entry and passes it to the common batch helper. run_test_client_batch.sh:148–198 exports EDGION_TEST_K8S_MODE=true and invokes test_client -g with the resource/item pair. The suite uses the resolved invocation HTTP port, so this is not another hard-coded-listener issue. run_k8s_integration.sh:6 chooses the Kubernetes conf tree by default, and 2879–2881 applies that tree. The Kubernetes README explicitly says there is no runtime conversion from local fixtures.

The local fixture supplies the missing dependencies: integration/conf/EdgionBackend/SingleProvider/05_EdgionPlugins_ai-proxy.yaml:191–218 declares ai-proxy-priority-retry-quota with Priority selection, a 20-token one-hour identity quota and Reject; 06_HTTPRoute_ai-proxy.yaml:280–310 declares ai-retry-quota.example.com, the corresponding ExtensionRef, one retry on 503, and the failing then healthy backend references. The complete corresponding Kubernetes files contain 172 and 189 lines respectively and declare neither resource. Literal searches of the full Kubernetes conf, scripts and deployment trees find neither the host nor the plugin identity. Other HTTPRoutes attached to the shared AI Gateway declare different exact hostnames; the existing nonquota retry route uses ai-retry.example.com and a different plugin. It does not supply this case's quota owner. A suite-directory existence check or static inventory-name comparison cannot detect this incomplete fixture dependency.

There is a feasible, bounded fixture repair. Add the missing Kubernetes-owned EdgionPlugins and HTTPRoute declarations through the existing SingleProvider fixture publication path. Preserve their object namespace, host, plugin identity, Priority ordering, 20-token quota, Reject action, one retry on 503 and request/backend deadlines. Adapt the plugin's Redis reference to the existing edgion-test/redis-test LinkSys, and adapt the healthy backend reference to single-provider-fixture-provider. Keep fixture-provider-retryable first. The complete current Kubernetes backend fixture already supplies both backends, including the real test-server fail-503 endpoint, and the existing Redis fixture and ordinary quota cases already supply the in-cluster dependency. Do not copy the local default/redis-test reference or healthy backend name unchanged.

An explicit, narrowly justified Kubernetes scope exception would be an alternative only if this contract could not be exercised with the supported topology. The current selected suite, existing provider backends, Redis dependency and existing nonquota retry route demonstrate the needed mechanisms. There is no current exception for SingleProvider. Skipping this case under Kubernetes, removing the suite selection, weakening the two-attempt ledger or replacing the Redis assertion with a synthetic success would discard supported coverage rather than complete it. A small repository-owned fixture-contract check for this particular host, ExtensionRef, retry ordering and namespace-adjusted dependencies can guard later publication drift; no new runtime registry or broad fixture-generation framework is needed.

The original kubernetes-dynamic-scenario-inventory-parity page includes static inventory in its scope but explicitly limits its historical live evidence to listed dynamic scenarios, not a complete static sweep. The current validator compares static Resource/Item names, which correctly finds SingleProvider registered and does not inspect this case's resource dependency closure. The Kubernetes fixture-boundary page documents narrow unrelated dynamic exceptions. Neither page accepts a selected static case whose required fixtures are absent. Current architecture artifacts and pending-task searches did not identify an existing finding for this retry-quota fixture omission. ARCH304 owns dynamic scenarios missing executable Kubernetes registration; this suite is already selected and its omitted fixture dependency is a distinct correction. ARCH264/265 lifecycle ownership, ARCH266 Controller status selection and ARCH296 resolved listener consumption do not repair it.

Future verification should keep the complete original SingleProvider case set, check the authored Kubernetes declarations against the retry-quota dependency contract, and run the selected suite against current Kubernetes images with the existing Redis and provider endpoints. Require the first request's 503/200 ledger, real Redis charge equal to both attempts, winning-response summary 11/7, and the second request's 429 with zero upstream attempts. Preserve authenticated diagnostics, credential redaction, existing request-only BodyStorage and streamed response ownership, and the production quota/runtime lifecycle. No production logging, metrics, transport, timeout policy or workqueue changes are required.

This review fully read the primary implementation and its embedded tests, the deciding local and Kubernetes fixtures, the actual runner/helper chain, relevant provider-fixture implementation and tests, and original owning knowledge. No build, checker, test, network call or repository mutation was performed.
