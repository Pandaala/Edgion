# Separate unavailable TCP listeners from ConnectionFilter denial

`StreamPluginsTestSuite` in `edgion-tests/src/client/suites/gateway/stream_plugins/stream_plugins.rs` treats failures before a TCP connection is established as evidence that the Gateway's ConnectionFilter rejected it. `test_tcp_denied` passes both every `TcpStream::connect` error and the three-second connection timeout. `test_tcp_qualified_name_rejected` has equivalent passing branches. `test_tcp_denied_multiple` counts a failed or timed-out connection toward all five successful denials. These branches do not observe the configured filter. An unavailable31271 socket reports a passed single denial and five passed repeated denials; an unavailable31272 socket reports a passed qualified-reference rejection.

The actual fixture topology makes this distinction material. The HTTP control uses31270 and the bare-name allow case31269, while the two negative policies use31271 and31272. Success on either positive physical listener does not establish availability of the tested negative listener. The suite can consequently report policy denial while the tested TCP target is absent or unreachable, even when its positive controls work. This is a source-derived assertion witness, not an observed outage or a claim that any particular integration run passed incorrectly. The canonical inventory correctly distinguishes all four sockets; collapsing them into one context port or redesigning their topology would lose required coverage.

The actual Gateway owner is an early filter after TCP accept, before PROXY parsing, TLS negotiation or HTTP processing. `add_tcp_listener` creates the TCP service and installs `GuardFirstConnectionFilter`, which delegates to `StreamPluginConnectionFilter`. The bridge pins the immutable connection view and evaluates Stage1 policy, returning false for unavailable policy or plugin denial. The original no-tracing decision explicitly preserves this pre-protocol boundary and its absence of a protocol access-log context. It does not define an external firewall, SYN-drop policy or missing listener as successful plugin evaluation. The qualified Gateway fixture deliberately supplies `edgion-test/allow-all-ips`; the original same-namespace contract requires an unqualified Gateway attachment and fail-closes this value. Actual publication and bridge test bodies cover the invalid sentinel, normalized bare key, unavailable-policy denial and ready connection views. None turns arbitrary connection-establishment failure into proof of this path.

Make the three existing negative probes fail an unavailable or timed-out connection instead of counting it as filter success. Own their wire evidence narrowly: establish the intended TCP connection, then retain bounded observation of prompt EOF or a supported peer-close/reset outcome without received application data. A pre-establishment reset should only remain an accepted outcome if a supported-platform protocol regression independently establishes that this exact immediate Gateway close is surfaced there; neither a generic connection-error match nor a timeout supplies that evidence. An unclassified establishment error must fail. Preserve each current connect/read deadline and the owning thirty-second TestCase deadline, prompt-close semantics, the qualified-reference policy distinction, and all five repeated attempts. Data returned by the denied listener and an established connection that remains idle past the rejection deadline must still fail.

Keep both positive controls and all five case identities. The bare-name positive case intentionally establishes allow-through by receiving application bytes from the real TCP echo fixture; this recommendation does not replace it with full-message identity testing or change its admission subject. Preserve separate HTTP, denied TCP, qualified TCP and bare-name TCP listener selection. No production filter, reference authorization, plugin publication, resource schema, fixture topology or TLS backend change is required. In particular, do not add Stage1 tracing, a new generic counter, a parallel rejected-connection log sink or a public test seam to compensate for the accepted observability boundary.

The minimum benefit is that an absent or unreachable negative target becomes a failed prerequisite rather than successful policy evidence. This does not make every later EOF uniquely attributable to a plugin: downstream routing/backend closure remains a distinct limitation. Reading only Controller status would be a different control-plane assertion and would discard the current wire-admission checks; a healthy control on another socket is also insufficient. Future verification should hold the HTTP and bare allow controls healthy while the negative target is unavailable and require failed results, then exercise actual deny-all and qualified-reference fail-close paths with prompt accepted-connection closure. Preserve the allowed byte flow, repeated rejection count, fixture identities and deadlines.
