# Require observed Listener no-conflict verdicts

The two no-conflict cases in PortConflictTestSuite accept missing Listener observations as successful conflict detection. `test_cross_gateway_no_conflict` maps an absent `http` Listener status to `false` with `unwrap_or(false)`. `test_no_conflict_diff_hostname` explicitly returns success when either `api` or `web` is absent. When Listener entries exist, `is_listener_conflicted` returns false for a missing Conflicted condition or any value other than True. A decoded Gateway with status={} or incomplete listener conditions therefore satisfies the claimed no-conflict result without containing the expected verdicts.

The actual current producer does not use omission for Listener no-conflict. GatewayHandler::update_status computes conflicts from ListenerPortManager and emits Conflicted=False/NoConflicts for each nonconflicting declared Listener. It deliberately removes Gateway-level ListenersNotValid when no conflicts exist, so absence of that aggregate condition is legitimate and must remain accepted. The distinction is between an optional aggregate conflict flag and the required per-Listener observation; the test collapses both into the same Boolean absence convention.

A concrete source-level witness is a producer regression omitting Listener statuses or their Conflicted conditions for a valid nonconflicting Gateway. The cross-Gateway case can accept two status objects with no http observations. The different-hostname case accepts a status object with no api/web observations, and also accepts both named entries with empty condition arrays. These representations deserialize through the current private optional fields. The regression's missing verdict is exactly what these individual tests should detect. Other suite cases may still fail; this finding does not claim that every complete matrix passes or that a deployed Controller currently omits these fields.

The real Kubernetes execution has a supporting manifestation in `edgion-tests/k8s/scripts/common/run_test_client.sh`. The PortConflict branch substitutes its own kubectl/jq checks and exits without invoking the Rust suite. Its different-hostname case also accepts whenever no ListenersNotValid=True or named Conflicted=True exists, even if api/web observations are missing. The same wrapper already has a suitable narrow `check_listener_not_conflicted` predicate requiring a named entry with Conflicted=False and uses it in the cross-Gateway nonconflict branch. Correcting only the Rust case would therefore leave the normal Kubernetes different-hostname path's evidence gap unchanged.

Require the exact declared Listener entries and an explicit Conflicted=False verdict for every Listener asserted to be nonconflicting. Use a fallible case-local selection/read result rather than mapping absent data to false. Treat missing entries, missing conditions and Unknown as absent evidence or a bounded pending observation, then fail when the existing owning deadline expires. Preserve the legitimate absence of Gateway-level ListenersNotValid and continue rejecting its True value. Use the actual declared Gateway namespace/name and Listener names, authenticated Admin access in Rust and existing kubectl context in the wrapper. Reuse `check_listener_not_conflicted` for both api and web in the Kubernetes case; retain its existing unexpected-True failure checks. Do not introduce a generic status framework or modify production status.

Keep all three Rust case identities, both same-port cross-Gateway fixtures, the different-hostname fixture, the internal-conflict True assertions, shared topology and bounded case/read behavior. The tests inspect Controller conflict status, not socket binding or Gateway data-plane acknowledgements; add no traffic request, metric, log, new condition family, second topology or TLS implementation. Native Gateway status remains conditions/listeners; it must not be projected through the custom-resource controllers[] helper proposed by ARCH266. The Gateway schema and native current-status capture independently falsify that envelope analogy.

The existing real ListenerPortManager unit bodies establish identical-hostname conflict, distinct-hostname allowance and cross-Gateway allowance. Gateway handler tests explicitly find named Listener conditions rather than accepting absence. They protect production computation but do not replace these live readers' evidence boundary. An alternative is to reuse a genuinely existing narrow typed Listener-condition reader, provided it preserves exact identity and missing-observation failure; merely deleting the success message or checking that status exists does not address empty listener/condition arrays.

The internal Kubernetes absent-resource branch separately assumes admission rejection, and the strict apply script deliberately excludes that internal-conflict fixture. It is not proof of an executed admission attempt. This is recorded as a distinct deferred topology/admission-evidence limitation rather than folded into the Listener verdict correction. The wrapper's historical acceptance of both cross-Gateway conflict policies is likewise separate from missing observations. ARCH338 concerns gRPC transport failures accepted as route denial; ARCH296 concerns resolved data-plane listener ports; neither supplies this native Listener observation remedy.

Future focused tests should reject status={}, an omitted expected Listener, missing Conflicted, Unknown, and a stale or malformed observation; accept the correctly named False verdicts with an absent ListenersNotValid aggregate; and continue rejecting any expected Listener's True verdict. Cover the same sparse and correct documents through the actual Kubernetes different-hostname jq checks. Preserve internal-conflict positive observations and existing algorithm regressions. No tests, builds, requests, shell harness execution, repository mutations or performance measurements occurred.
