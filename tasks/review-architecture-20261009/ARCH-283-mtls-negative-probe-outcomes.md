# Separate probe setup and transport failure from expected mTLS rejection

The existing mTLS negative cases own a server authentication assertion, but their success boundary accepts failures that occur before that assertion can be observed. `test_mutual_with_invalid_cert` in `edgion-tests/src/client/suites/edgion_tls/mtls/mtls.rs` returns a passing result for every `create_mtls_client` error. That helper includes certificate/key filesystem reads, PEM parsing, target resolution and client construction. The generated invalid identity is deliberately a valid certificate/key signed by an untrusted CA; a missing `invalid-client.key` is therefore a broken test precondition, not Gateway rejection. The invalid-certificate and SAN-mismatch request branches also pass every send error without establishing that it was the expected server-side TLS rejection. Other positive cases and SAN client-construction failures correctly fail their preparation errors.

The actual static caller registers this suite in targeted and aggregate EdgionTls execution. Local and Kubernetes fixtures select the same `Mutual`, `OptionalMutual`, SAN whitelist, chain-depth and no-CA `Terminate` policies. The generator constructs the nonmatching SAN identity under the trusted client CA, isolating the allowlist witness. The production verify callback distinguishes chain failure from leaf-only allowlist evaluation, and its real unit bodies cover those decisions and one terminal audit. This is a test-evidence finding; no production mTLS bypass, live incident or whole-matrix false pass is claimed.

A supporting existing owner, `edgion-tests/src/client/suites/gateway/tls/frontend_validation/mod.rs:170-221`, has the same invalid-client preparation-success branch. It is supporting evidence only, not primary coverage. A second primary owner, `edgion-tests/src/client/suites/edgion_tls/mtls_failclose/mtls_failclose.rs`, has an equivalent negative-outcome gap at its subprocess boundary: the ten-second watchdog kills the child then parses its output without returning a timeout failure. The two EdgionTls cases accept any incomplete handshake directly in Kubernetes mode, where the suite explicitly omits unavailable local ssl.log evidence. Empty/missing negotiated fields or a watchdog-terminated child can therefore be accepted without an observed policy rejection. The frontend-validation case additionally requires `CONNECTED` and selected invalid listener conditions; these are meaningful stronger checks but do not distinguish a child timeout after TCP connection from the expected listener rejection. Local EdgionTls cases additionally require an existing audited rejection record; they are stronger than the Kubernetes branches and are not claimed to pass without that record.

Keep a narrow negative-probe outcome owner in each existing helper/case. Fail certificate/key loading, parsing, DNS resolution and client-construction errors before sending. Classify a child deadline as a failed operation, preserve child termination/reaping, and retain genuine TLS alert/nonzero-exit rejection as a distinct outcome rather than treating every nonzero exit as environmental failure. A negative policy assertion must establish the intended listener was reached and yielded the expected TLS/policy denial; connection refusal, timeout, missing parsed evidence or unrelated request failure cannot supply that proof. Where reqwest does not expose a reliable distinction, use the existing test TLS tooling or existing scoped audit evidence and review its exact error classification during implementation. Do not replace this with another broad display-string check or an assertion that any HTTP response means success.

Preserve all eleven mTLS case identities and all three fail-close identities, complete positive cases, per-SNI/port selection, valid untrusted identity and trusted SAN-mismatch identity, client-chain/bundle semantics, and Terminate's absence of client-CA requirements. Retain authenticated status polling and the actual frontend listener condition owner. Preserve the documented Kubernetes log-availability limitation instead of requiring an unavailable host file or weakening it to a skip. No production logging, metrics, TLS implementation, shared subprocess framework, new dependency, certificate data disclosure or Gateway rustls support is needed. The viable local improvement is changing acceptance ownership; rearranging test names alone has no value.

Future tests should distinguish missing identity/key, invalid PEM, failed target resolution, child timeout, connection refusal, incomplete/missing fields, genuine expected TLS rejection and unexpected completed handshake. Retain live topology tests for wire policy and existing production unit tests for callback decisions. Test pure outcome decisions without networked unit environments, and preserve meaningful case errors. This cause differs from ARCH282's positive cipher-policy evidence and ARCH288's synchronous unbounded child waits: fail-close already has a watchdog, but currently consumes its timeout as handshake evidence.

Both primary pairs were fully read, with actual fixtures, generator statements, registrations, production verify-mode/allowlist seams and actual unit bodies. Original testing assertions and TLS leaf-only, verify-before-identity and Terminate-without-CA decisions were read and checked against current code. Source-only review: no generated keys, OpenSSL processes, builds, tests, network operations or production changes. Exact transport-error classification and cancellation behavior remain implementation review obligations. Candidate awaits independent falsification.
