# Attribute the backend SAN rejection to its canonical request diagnostic

BackendTlsSanTestSuite::test_san_hostname_mismatch accepts every received5xx response as proof that the Gateway enforced BackendTLSPolicy.subjectAltNames. It fails reqwest transport errors, but a Gateway-generated502 caused by an unavailable upstream or a backend-produced503 satisfies the same success predicate without establishing SAN verification. The preceding positive case is useful readiness evidence; it does not prove the later exchange reached certificate verification. A source-level witness is a correct positive exchange followed by backend unavailability while SAN enforcement is incorrectly bypassed: the negative case still passes. This does not claim an executed regression, deployment incident or complete-suite false pass.

The primary owner is edgion-tests/src/client/suites/gateway/tls/backend_tls_san/backend_tls_san.rs. Both cases use the canonical Gateway/TLS/BackendTLSSAN context port and declared paths. The authored local and Kubernetes fixtures live under HTTPRoute/Backend/BackendTLSSAN, not Gateway/TLS. Their two Service identities reach the same port30051 server. Both policies use backend.example.com as the TLS validation hostname and the same trusted CA; only the additional Hostname subjectAltNames differs, using backend.example.com for the positive and wrong.example.com for the negative. Thus this test targets additional SAN enforcement rather than ordinary SNI/CA selection.

The production owner already provides exact attribution. peer_builder::create_tls_peer installs the canonical certificate-extraction/SAN-validation handshake hook for nonempty subjectAltNames. pg_connected_to_upstream::connected_to_upstream reads BackendSanValidationResult from the SSL digest, records EdgionErrorCode::BackendTlsSanValidationFailed when the result fails, and returns InvalidCert. The existing bounded request diagnostic history is serialized through AccessLogEntry; its string code is BackendTlsSanValidationFailed. Real backend_san unit bodies distinguish exact/wildcard/URI matches, nonmatches and typed display-prefix exclusion. These protect pure matching, but do not prove the live negative response exercised this connection hook.

Keep the actual5xx assertion and require the same exchange's existing error diagnostic BackendTlsSanValidationFailed. Send the negative request with the existing access_log: test_store opt-in header and a fresh unique test marker through traceparent_for_marker, query through the existing TestContext::access_log_client and bounded retry helper, and require has_diagnostic(error, BackendTlsSanValidationFailed) on that exact current request. The context already owns local/Kubernetes Admin endpoint selection, and AccessLogClient carries the existing bearer token. Missing, unavailable, malformed or timed-out diagnostic evidence fails; a stale entry under a reused marker cannot satisfy the assertion. Preserve the owning thirty-second case deadline, declared Host/path/listener and current positive response/body check. Retain canonical diagnostics as the traffic observation owner; no new counter, trace log, error string disclosure or response-header probe is required.

The correction is confined to this test's rejection-evidence ownership. Keep both original case identities, the shared trusted30051 producer, different additional SAN constraints, supported BoringSSL behavior, existing fixtures and actual500-class outcome handling. Do not alter production TLS matching, peer pooling, Gateway error mapping, body policy or Controller processing. Request diagnostics are bounded; this small fixture should require its specific rejection entry rather than weaken the check when evidence is missing or truncated. If a future fixture genuinely exhausts that history before SAN validation, redesign its bounded witness separately rather than adding unbounded diagnostics.

A positive readiness control alone cannot distinguish a later unreachable backend from policy enforcement. Restricting the response to502 alone is also insufficient because upstream connection failures produce502. Reusing the existing canonical diagnostic gives both the policy boundary and exact request identity without a generic negative-test framework or new observability. Original upstream-TLS architecture describes the additional SAN hook, the typed-SAN guard retains canonical classification, and the access-log contract owns request failures. Historical negative-test evidence illustrates unrelated failures accepted as rejection; its old mutation results are not fresh proof here. ARCH283 concerns downstream client-authentication preparation, ARCH338 a gRPC no-route representation, and ARCH340 an HTTP request-length response; none corrects this upstream SAN hook's attribution.

Future verification should require failure for an unrelated502/503 without the exact diagnostic, missing/stale/unavailable access-log evidence and a successful response after bypassing the SAN hook. Genuine additional-SAN rejection with the matching fresh diagnostic should pass, while the existing positive case remains successful against its current producer. Preserve the real matcher unit bodies, listener mapping and both local/Kubernetes suite registrations. This review read the complete primary, authored fixture sets, actual peer/hook/diagnostic owner, existing access-log readers and relevant original knowledge. No build, test, service, network request, mutation or performance measurement was performed.
