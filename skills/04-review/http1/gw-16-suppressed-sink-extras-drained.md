# Suppressed Follow-Up Tasks Drain Their Sink Extras

## Conclusion

After cache admission and predicted-size accounting observe a response task's
`ResponseBodySink` extras, every H1, H2, and custom pump must drain those extras before returning
from the downstream-body suppression guard. Leaving them queued makes a later task in the same
pump batch observe and cache or count the same bytes again.

## Core Rationale

`ResponseBodySink::reset_batch` runs only at a pump batch boundary. It cannot isolate two tasks
already collected into the same batch. The normal output path drains through
`drain_emitted_chunks`, and non-streaming cache admission reads extras with `peek_extra` before
the suppressed task is discarded. The suppression guard therefore owns the matching
`take_extra` call.

The drain applies to every suppressed follow-up task and precedes failure handling. A failed task
must still mark the upstream non-reusable and abort incomplete cache admission after its extras
have been cleared.

## Fix Suggestions Not Accepted

- Relying on `reset_batch`: it runs too late for later tasks in the current batch.
- Draining only failed tasks: successful suppressed body tasks are the ordinary corruption path.
- Moving the drain before cache admission: the current task's generated bytes must still be
  cached and counted once.
- Fixing only H1: H2 and custom pumps share the same sink lifecycle.

## Regression Boundary

Use a non-streaming cache backend so live upstream tasks reach the suppression guard rather than
the streaming-partial-read discard branch. The origin must generate multiple body callbacks in
one pump batch, the filter must emit a distinguishable sink chunk per callback, and a follow-up
cache hit must exactly match the callback-order representation with no duplicated bytes.
