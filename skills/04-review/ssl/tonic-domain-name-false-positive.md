# tonic ClientTlsConfig Not Calling domain_name() is Not a Vulnerability

## Conclusion

`tonic::transport::ClientTlsConfig` not explicitly calling `.domain_name()` **does not constitute MITM risk**.

## Reasons

- tonic by default extracts hostname from the `Endpoint` URI's host part, used for SNI in the TLS handshake and for certificate SAN/CN verification
- Edgion's `build_grpc_uri()` constructs URIs of the form `https://hostname:port`; the hostname comes from the user-configured connection address
- In K8s the connection address uses the Service DNS name (e.g., `edgion-controller.ns.svc`); the certificate SAN matches it and verification passes automatically
- Certificates are generated by the project's own `generate_certs()`; the CA is fully self-controlled; there is no scenario of "another service certificate signed by the same CA leaks"

## Decision Rule

When a review reports "TLS client not calling `domain_name()` causes MITM risk", check:

1. Does the Endpoint URI contain a correct hostname (not a bare IP)? → If yes, tonic's default behavior is sufficient
2. Is the certificate CA self-controlled? → If yes, there is no "third-party same-CA certificate" attack surface
3. Is the connection address operator-configured? → If yes, configuration correctness is the operator's responsibility

All three satisfied → not a real issue, close.
