# Review Knowledge Base

This directory stores reusable conclusions from Edgion project reviews. Priority recording targets:

- False positives or over-graded findings already confirmed against code
- Issues that must be judged according to project design semantics
- Decision criteria that can be reused directly in future reviews

## Review issue fix workflow

To process a single finding from any `tasks/review-*/` directory, use [`fix-review-issue.skill`](fix-review-issue.skill).
Invoke it (or the `/fix-issue` global slash command) when the user says "review issue", "handle issue", "next issue", or any equivalent phrasing in another language.
Supports auto-detection of the issue directory, issue ID lookup, or explicit path arguments.

Load on demand:

- For memory issue findings, first read [memory-leak/not-a-memory-leak.md](memory-leak/not-a-memory-leak.md)
- For CPU/Memory performance findings:
  - **General methodology** (how to determine if it is a false positive) → [cpu-memory/performance-review-methodology.md](cpu-memory/performance-review-methodology.md)
  - **Confirmed false-positive scenarios** (concrete cases) → [cpu-memory/not-a-performance-issue.md](cpu-memory/not-a-performance-issue.md)
  - When reviewing `record_cross_ns_refs` / similar reconcile-handler findings of the form "loop with one lock per item should be batched / done within a single lock," first read the section "Route handlers `record_cross_ns_refs` loop `add_ref` is not a lock hotspot" in [cpu-memory/not-a-performance-issue.md](cpu-memory/not-a-performance-issue.md) — K8s reconcile is an event-level cold path; for a single route with 1-10 backend_refs, total lock overhead is microseconds; batching would require changing 5 handlers with zero observable benefit
  - When reviewing `BidirectionalRefManager` / `SecretRefManager` / `ServiceRefManager` / `CrossNamespaceRefManager` findings of the form "no GC / expiry / periodic check, refs will permanently linger," first read the section "`BidirectionalRefManager` lacking GC/expiry is not a memory leak" in [cpu-memory/not-a-performance-issue.md](cpu-memory/not-a-performance-issue.md) — it is an index of the K8s resource graph rather than a cache; clear-then-readd pattern + delete path + watch resync + leader-switch reset already form a four-layer closed loop; adding GC would conflict with the reconcile state machine
- When reviewing `RwLock`/`Mutex` `.unwrap()`, first read [rwlock-unwrap/rwlock-unwrap-rule.md](rwlock-unwrap/rwlock-unwrap-rule.md)
- When reviewing handlers, first read [handler-requeue/handler-requeue-rule.md](handler-requeue/handler-requeue-rule.md)
- When reviewing DSL `log_warn(value)` / `log_error(value)` writes to PluginLog: dynamic values are written via `push_sensitive`, with behavior controlled by the `[access_log_sensitive]` global switch (default off → plaintext, replace → `***`, wrap → `<E>...</E>`). Regular plugin code should use `push_fmt` + `sensitive(...)` to mark sensitive parameters. If the finding is "the value is still visible after applying redaction" — this is the expected behavior when default is off; the deployer enables replace/wrap according to compliance requirements
- When reviewing observability (logs/metrics/access log), first read [observability/observability-review-rule.md](observability/observability-review-rule.md)
- When reviewing TLS/SSL client configuration, first read [ssl/tonic-domain-name-false-positive.md](ssl/tonic-domain-name-false-positive.md)
- When reviewing OpenSSL/rustls backend gaps, skip — known limitation; BoringSSL is the only production backend, see `tasks/todo/multi-tls-backend-gaps.md`
- When reviewing ctx_set template/variable design, first read [ctx-set/ctx-set-design-decisions.md](ctx-set/ctx-set-design-decisions.md)
- When reviewing LB/BackendSelector concurrency (ArcSwap TOCTOU, init idempotency), first read [concurrency/lb-false-positives.md](concurrency/lb-false-positives.md)
- When reviewing route architecture consistency (TCP/UDP/TLS/HTTP/gRPC cross-protocol comparison), first read [architecture/route-architecture-consistency.md](architecture/route-architecture-consistency.md)
- When reviewing `plugin_runtime.rs` "god object / huge file / should use registry / should use enum_dispatch / should split files by stage" findings, first read [architecture/plugin-runtime-god-match.md](architecture/plugin-runtime-god-match.md) — the central exhaustive match is a deliberately retained design tradeoff (compile-time exhaustiveness check + plugin panorama visible + stage constraints centralized); enum_dispatch refactoring brings no benefit to hot-path performance; related fix suggestions are not accepted
- When reviewing ACME `service.rs` "huge phase function should be split / global singleton `ACME_SERVICE` should use DI / handle_resource_check is too long" findings, first read [architecture/acme-service-shape.md](architecture/acme-service-shape.md) — the ACME protocol has a naturally linear flow + Controller leader-elected single-active model; splitting by phase is negative-value, switching to DI is illusory benefit; real defects (swallowed errors, silent UTF-8 fallback) have been fixed. Only newly emerging swallowed-error / silent-fallback findings are accepted
- When reviewing `EdgionAcmeHandler::parse` "notify_resource_changed is unconditional / should gate on spec change" findings: **this was fixed (c1-013)**. `parse` now gates `notify_resource_changed` on `spec_changed || creds_changed` — spec_changed compares `metadata.generation` with the Accepted condition's `observed_generation` (written by `update_status` each cycle); creds_changed detects ResolvedRefs status/reason transitions. Restart resilience is handled by `scan_all_acme_resources` in `start_acme_service`. If a finding claims the guard is missing, verify the current code in `edgion_acme.rs:parse` before re-reporting
- When reviewing "file X has too many lines, should be split / two modules look similar, should extract common code / new X automatically becomes a public API" or other refactoring findings driven by line count or surface similarity, first read [architecture/size-and-similarity-heuristics.md](architecture/size-and-similarity-heuristics.md) — three pieces of evidence must be provided: real duplication (≥2 places with 30+ similar lines) / real coupling leak / lower tracking cost after splitting; missing any one means closed. Already audited points: types/resources/common, types/mod.rs glob re-export, edgion_acme outcome mapping, rate_limit vs rate_limit_redis, runtime/store/config.rs, unified_auth/mod.rs.
- When reviewing jwt_auth `load_credentials_from_secret` "4-path duplication / should extract helper / function too long" findings, first read [architecture/jwt-auth-credentials-source-paths.md](architecture/jwt-auth-credentials-source-paths.md) — the 4 data sources differ structurally in type / error labels / asymmetric branch behavior; "duplication" is appearance only; the function is cached and called only once; error wording is verified character-by-character by 25 tests; refactoring fix suggestions are not accepted
- When reviewing Basic Auth "username enumeration timing difference" findings, first read [auth-timing/basic-auth-username-enumeration.md](auth-timing/basic-auth-username-enumeration.md) — in gateway scenarios, code-layer dummy verify is an anti-pattern, closed via documentation; code fix suggestions are not accepted. The plugin no longer supports bcrypt at all (Envoy / Kong-aligned); only `{SHA}` / `$apr1$` / `$1$`
- When reviewing Basic Auth "should support bcrypt / should add result cache / plaintext load should bcrypt-hash" findings, first read [auth-timing/basic-auth-no-bcrypt.md](auth-timing/basic-auth-no-bcrypt.md) — bcrypt was deliberately removed alongside the LRU result cache to align with Envoy / Kong; only `{SHA}` / `$apr1$` / `$1$` are supported, plaintext is upgraded to `{SHA}` on load; heavy auth schemes belong behind `forward_auth` / ext authz; `local_auth` (Controller admin) retains bcrypt and is unrelated
- When reviewing Key Auth "HashMap lookup is not CT" findings, first read [auth-timing/key-auth-hashmap-not-ct.md](auth-timing/key-auth-hashmap-not-ct.md) — SHA-256 preprocessing eliminates exploitability; not a real attack surface; linear CT scan fix suggestions are not accepted
- When reviewing ForwardAuth "default forwards all credential headers" findings, first read [forward-auth/default-header-forwarding.md](forward-auth/default-header-forwarding.md) — consistent with Traefik/Envoy mainstream defaults, URI is admin-static-configured, the documentation clearly explains the three modes; fix suggestions to change default / force allowlist are not accepted
- When reviewing OpenidConnect "`useNonce` / `usePkce` default off" findings, first read [oidc/nonce-pkce-defaults.md](oidc/nonce-pkce-defaults.md) — OIDC spec defines them as OPTIONAL, mainstream gateway defaults are consistent; server-side exchange + state already cover the major threats; documentation has added a recommendations section. Fix suggestions to change code defaults are not accepted
- When reviewing Admin API "CORS open" / "should add origin allowlist" findings, first read [admin-cors/admin-cors-same-origin-rule.md](admin-cors/admin-cors-same-origin-rule.md) — Edgion adopts a same-origin deployment architecture (dev Vite proxy / prod dashboard embedded); not attaching a CORS layer to the Admin API is an architectural decision; fix suggestions to "introduce cors_allowed_origins config" are not accepted
- When reviewing CORS plugin "`*.domain` shorthand does not match http" findings, first read [cors/subdomain-wildcard-https-only.md](cors/subdomain-wildcard-https-only.md) — Edgion's bespoke syntactic-sugar deliberate design; HTTPS-only matches operator intuition; http needs are declared explicitly via `allow_origins_by_regex`; fix suggestions to "revert to `https?://`" are not accepted
- When reviewing findings of the form "an unsafe mode (such as `skip_tls`, `AllowInsecureFallback`) should be forbidden / time-limited at the code level," first read [observability/system-error-state-metric.md](observability/system-error-state-metric.md) — Edgion uses the `edgion_system_error_state` gauge to register startup-phase degraded states; operators configure Alertmanager as a backstop; preserving the emergency escape hatch is a product decision
- When reviewing RealIp `maxTrustedHops` "should be required / change default / remove" findings, first read [real-ip/max-trusted-hops-opt-in.md](real-ip/max-trusted-hops-opt-in.md) — opt-in is a deliberate design: default `None` keeps Nginx compatibility with zero breakage; the main defense is precise `trustedIps` configuration, `maxTrustedHops` is a secondary defense
- When reviewing ForwardAuth / Webhook "`uri` lacks internal IP filtering / SSRF risk" findings, first read [ssrf/forward-auth-webhook-ssrf.md](ssrf/forward-auth-webhook-ssrf.md) — ForwardAuth itself needs to call internal services (RFC 1918 is a legitimate target); literal IP blocking has very narrow coverage and cannot defend against DNS rebinding; the correct defense layer is K8s RBAC + NetworkPolicy + cloud-side IMDSv2; code-level IP filtering fix suggestions are not accepted
- When reviewing loopback, link-local, or metadata address protection on upstream-rewrite or upstream-selection paths such as DynamicExternalUpstream / RegionRoute / DynamicInternalUpstream / DirectEndpoint / RequestMirror / EndpointSlice LB, first read [ssrf/upstream-address-safety.md](ssrf/upstream-address-safety.md) — allowlist / backendRefs are the authorization boundary, not equivalent to safety of the final dial address; production upstream defaults reject loopback + link-local; only integration-testing mode may permit loopback for local fixtures on Endpoint-derived paths; RFC1918 private networks remain allowed
- When reviewing `EdgionTls` "validator should reject `TLS1_0` / `TLS1_1`" findings, first read [edgion-tls/tls-version-operator-choice.md](edgion-tls/tls-version-operator-choice.md) — an opt-in channel deliberately retained for legacy clients; defaults are TLS 1.2+ when not configured; documentation and schema have multi-layer ⚠️ warnings; operator makes an informed choice; code-level hard-rejection fix suggestions are not accepted
- When reviewing IP restriction / rate limiting "`ClientIp` can be spoofed via XFF when RealIp is not configured" findings, first read [ip-restriction/ip-source-client-ip-false-positive.md](ip-restriction/ip-source-client-ip-false-positive.md) — premise is wrong: when RealIp is not configured `remote_addr` is initialized to TCP IP, XFF is not read, so the attack scenario does not hold; doc comment has been corrected
- When reviewing IpRestriction deny-log assertions or test fixtures after the 2026-05-14 IP-list group refactor, first read [ip-restriction/group-name-in-deny-log.md](ip-restriction/group-name-in-deny-log.md) — deny logs now carry the matched group name (`"deny:group=<name>"`, `"deny:not-in-allow"`, `"deny:default"` / `"allow:default"`, `"deny:no-client-ip"`); confirm fixtures use the new literal format, not the legacy `"Allow ip match"` / `"Deny ip match"` strings
- When reviewing HMAC Auth "should add nonce dedup / Redis replay-protection store" findings, first read [hmac-auth/replay-protection-timestamp-only.md](hmac-auth/replay-protection-timestamp-only.md) — timestamp window + HTTPS + business-layer idempotency is the consistent layering of AWS SigV4 / Stripe / GitHub / Kong / APISIX; gateway-layer nonce storage is either inconsistent across instances or introduces a hard Redis dependency; code-level nonce dedup fix suggestions are not accepted
- When reviewing local admin JWT "still valid after logout / should add server-side blacklist / should switch to access + refresh" findings, first read [local-auth/jwt-revocation-stateless-tradeoff.md](local-auth/jwt-revocation-stateless-tradeoff.md) — same stateless tradeoff as Argo CD / K8s Dashboard; truly required revocation goes through `unified_auth` OIDC federation; for offboarding ops there are three alternatives — change password / rotate jwt_secret / shorten expiry; code-level blacklist fix suggestions are not accepted
- When reviewing HeaderCertAuth "Header mode single-layer CA matching / does not build full certificate chain" findings, first read [header-cert-auth/chain-verification-header-mode.md](header-cert-auth/chain-verification-header-mode.md) — in Header mode the upstream proxy already performed chain verification; single-layer matching is application-layer secondary filtering, consistent with Kong mtls-auth industry practice; webpki / chain-path construction fix suggestions are not accepted
- When reviewing HMAC Auth "unsigned headers can be tampered with / should sign all headers by default" findings, first read [hmac-auth/signed-headers-scope.md](hmac-auth/signed-headers-scope.md) — protocol design semantics, consistent with AWS SigV4 / Stripe / Kong; `enforce_headers` config already exists; "sign all by default" fix suggestions are not accepted
- When reviewing Redis rate limiting "fail-open should change to fail-close / change default to Deny" findings, first read [rate-limit/redis-fail-open.md](rate-limit/redis-fail-open.md) — operator tradeoff, `onRedisFailure: Deny` is already configurable, Kong / APISIX likewise default fail-open; "change default to Deny" fix suggestions are not accepted
- When reviewing Webhook Key Resolver "response not signed / should add HMAC verification" findings, first read [webhook-key/response-signature-not-needed.md](webhook-key/response-signature-not-needed.md) — Edgion actively calling external services is the OAuth Introspection / OPA ExtAuthz pattern (industry consensus relies on TLS rather than response signatures); URI is statically configured by the operator; the only value scenario for response signature = backstop for misconfigured TLS, which is operator error rather than a code gap; fix suggestions to introduce a `responseSignature` field are not accepted

- When reviewing timeout/duration `String` or `Option<String>` fields for "no schema-level format validation / malformed values fall back silently": **fixed (t1-010)**. `ClientTimeout` and `BackendTimeout` in `edgion_gateway_config.rs`, plus `HTTPRouteTimeouts.request/backendRequest`, `HTTPRouteRetry.backoff`, and `SessionPersistence.absoluteTimeout/idleTimeout` in `http_route.rs` all carry `#[schemars(pattern(r"^([0-9]+…)+$"))]` annotations that inject a JSON Schema `pattern` constraint into the CRD. The gateway runtime still has its own `parse_duration` + warn-and-fallback path; the schema constraint is the first line of defence at admission time. If a finding claims the pattern annotation is missing on one of these fields, verify the current source before re-reporting.

- When reviewing path-based ACL safety (misuse of `req.request_path`, direct read of `req_header().uri.path()`, raw write of `req_header_mut().set_uri()`, `RegularExpression` containing `%XX` literals, attacks beyond the commitment scope), first read [uri-normalization/SKILL.md](uri-normalization/SKILL.md)

Usage principles:

- Only write here after the conclusion has been verified against the current code and design semantics
- Keep content brief; only retain reusable judgment criteria, do not copy entire reviews
- If design goals change in the future, update the conclusions here in sync
