# Review Knowledge Base

This directory stores reusable conclusions from Edgion project reviews. Priority recording targets:

- False positives or over-graded findings already confirmed against code
- Issues that must be judged according to project design semantics
- Decision criteria that can be reused directly in future reviews

## Review issue fix workflow

To process a single finding from any `tasks/review-*/` directory, use [`fix-review-issue.skill`](fix-review-issue.skill).
Invoke it (or the `/fix-issue` global slash command) when the user says "review issue", "handle issue", "next issue", or any equivalent phrasing in another language.
Supports auto-detection of the issue directory, issue ID lookup, or explicit path arguments.

Load on demand:

- For memory issue findings, first read [memory-leak/not-a-memory-leak.md](memory-leak/not-a-memory-leak.md)
- For CPU/Memory performance findings:
  - **General methodology** (how to determine if it is a false positive) → [cpu-memory/performance-review-methodology.md](cpu-memory/performance-review-methodology.md)
  - **Confirmed false-positive scenarios** (concrete cases) → [cpu-memory/not-a-performance-issue.md](cpu-memory/not-a-performance-issue.md)
  - When reviewing `record_cross_ns_refs` / similar reconcile-handler findings of the form "loop with one lock per item should be batched / done within a single lock," first read the section "Route handlers `record_cross_ns_refs` loop `add_ref` is not a lock hotspot" in [cpu-memory/not-a-performance-issue.md](cpu-memory/not-a-performance-issue.md) — K8s reconcile is an event-level cold path; for a single route with 1-10 backend_refs, total lock overhead is microseconds; batching would require changing 5 handlers with zero observable benefit
  - When reviewing `BidirectionalRefManager` / `SecretRefManager` / `ServiceRefManager` / `CrossNamespaceRefManager` findings of the form "no GC / expiry / periodic check, refs will permanently linger," first read the section "`BidirectionalRefManager` lacking GC/expiry is not a memory leak" in [cpu-memory/not-a-performance-issue.md](cpu-memory/not-a-performance-issue.md) — it is an index of the K8s resource graph rather than a cache; clear-then-readd pattern + delete path + watch resync + leader-switch reset already form a four-layer closed loop; adding GC would conflict with the reconcile state machine
  - When reviewing `status_diff.rs::conditions_equal` (and the sibling parent/ancestor/listener matchers) findings of the form "O(n²) linear scan, should switch to HashMap for O(1) lookup," first read the section "`status_diff::conditions_equal` O(n²) Linear Scan on Bounded Condition Arrays is Not an Issue" in [cpu-memory/not-a-performance-issue.md](cpu-memory/not-a-performance-issue.md) — cold path (Controller status reconcile), n ≤ 10 hard-bounded, HashMap setup overhead likely regresses the actual workload; code-clarity rewrite suggestions are not accepted

Regular plugin code should use `push_fmt` + `sensitive(...)` to mark sensitive parameters.
