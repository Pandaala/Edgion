# 04 Review

For closed findings (previously fixed or accepted) see [CLOSED-FINDINGS.md](CLOSED-FINDINGS.md). ## RFC-compliance issue fix workflow

To process a single finding from `tasks/todo/rfc-review/` (`rfc-violation-*`, `rfc-naming-*`, `rfc-refactor-*`, or one section of `rfc-doc-comments-additions.md`), use [`fix-rfc-issue.skill`](fix-rfc-issue.skill).
Invoke it (or the `/fix-rfc` slash command) when the user says "fix RFC", "next RFC", "handle RFC", "review RFC findings", or any equivalent phrasing in another language.
The skill adds an explicit **Step 1.5 Design / Constraint analysis** that weighs the RFC clause against Gateway API conformance, existing `skills/` decisions, plugin SDK stability, hot-path performance, and operator escape hatches — RFC compliance is one constraint, not the overriding one.
RFC-divergence-accepted findings are recorded as per-finding files under [`rfc-divergence/`](rfc-divergence/) (one `<finding-id>-<slug>.md` per entry; see [`CLOSED-FINDINGS.md`](CLOSED-FINDINGS.md) for the ⚠️ rows that point into it).

## Usage principles

- When reviewing `forward_auth::send_error_response` "`let _ = resp.insert_header(...)` swallows errors / invalid headers from auth service leave no PluginLog trace" findings: **fixed (P3-g3-016)**. `send_error_response` now takes `plugin_log: &mut PluginLog` and emits `plugin_log.push_err("invalid response header")` when an `extra_headers` entry from the configured `client_headers` fails `insert_header`. The static `Content-Type` / `Connection` inserts and the `write_response_*` calls retain `let _ = ...` intentionally — the static headers cannot fail, and `write_response_*` failures mean the downstream connection is already closed (no actionable observability). The `extra_headers` values are pre-filtered by `HeaderValue::to_str()` at the call site (operator-configured `client_headers` echo from auth service response), so realistic failures are operator misconfiguration with a non-token byte in a header **name**. If a finding claims the `extra_headers` insert silently drops, verify the current `forward_auth/plugin.rs::send_error_response` before re-reporting. Generalised rule: data-plane error-response helpers that echo operator-configured header names should funnel insert failures through PluginLog, not `tracing`.

- When reviewing path-based ACL safety (misuse of `req.request_path`, direct read of `req_header().uri.path()`, raw write of `req_header_mut().set_uri()`, `RegularExpression` containing `%XX` literals, attacks beyond the commitment scope), first read [uri-normalization/SKILL.md](uri-normalization/SKILL.md)

- When reviewing proposals of the form "why not just use Rhai / mlua / rune / Boa instead of the custom VM", "add user-defined fn / closures / modules to EdgionDSL", "use Rhai's `Dynamic` / `OptimizationLevel` / `Package` system", or any similar engine-replacement / feature-import proposal, first read [dsl-design-decisions.md](dsl-design-decisions.md) — the four-constraint analysis (cross-process bytecode, in-engine sandbox, no user-fn / closures, no global mutable state) disqualifies every off-the-shelf engine; the memo also reverse-indexes the closed `dsl-vm-rhai-research` series so each historical finding maps to its current canonical home.

- When reviewing proposals to migrate DSL `Value::Str(Arc<str>)` to a SSO / `try_unwrap`-capable string type (`Arc<SmartString>`, `Arc<CompactString>`, `KString`, `EcoString`, etc.) for performance, first read [dsl-value-str/sso-migration-not-worth-it.md](dsl-value-str/sso-migration-not-worth-it.md)

- When reviewing federation `RegisterRequest` / `ControllerRegistry` / `ResourceAggregator` findings of the form "unbounded controller_id growth / memory amplification / SQLite explosion / missing TTL on offline rows": **fixed (common-center-03, 2026-05-16)**. `fed_sync::server::sync` now runs `validate_register_req` (controller_id non-empty + ≤ 253 B + no control chars; cluster ≤ 63 B + no control chars; env / tag / supported_kinds ≤ 32 items × 63 B each + no control chars) and `registry_capacity_exceeded` (cap 10_000; reconnect of a known id is always allowed) before any state mutation. The retention rule in `cpu-memory/not-a-performance-issue.md` still rejects TTL/eviction-sweep findings. If a finding claims the boundary checks are missing, verify the current `src/core/center/fed_sync/server/mod.rs` before re-reporting; if a finding proposes loosening or removing the caps, reject — they are the defence-in-depth that complements `common-center-01`'s mTLS work.

- When reviewing findings of the form "`Value::Map` has an unnecessary `Box`, remove it" / "Box adds an extra heap allocation per Map construction" / "why is only `Map` Boxed but not `List`/`Str`", first read [dsl-value-str/map-variant-is-boxed.md](dsl-value-str/map-variant-is-boxed.md) — `Map(Box<IndexMap<String, Value>>)` is intentional: it shrinks `size_of::<Value>()` from 72 → 24 B and per-request `VmState` stack frame from ~2.3 KB → ~0.83 KB; the `assert_value_size_invariant` test in `value.rs` locks the size at 24 B; do not propose unboxing — investigated 2026-05-15 across four candidate crates; outer-`Arc` defeats SSO for `SmartString`/`CompactString`; `kstring` 2.0.2 source review confirmed `KString::into_string` is NOT zero-copy (the `HeapStr` trait exposes no consuming method to extract inner `Arc<str>` for `try_unwrap`); only realized benefit is SSO on short-string construction (~5–15 alloc/request out of several hundred), insufficient to justify a new dependency + MSRV 1.95.0 lift + ~98 call-site diff. Defer until profiling shows DSL string allocation as a real bottleneck. Bespoke options (`Arc<Box<str>>` for zero-copy `into_string`, custom inline+arc enum) are catalogued in the memo with their trade-offs.

- When reviewing DSL `Constant::Regex` compilation "default 10 MB `size_limit` / `dfa_size_limit` means 256 × 10 MB = 2.5 GB DoS surface in `Vm::new` / `Validator::validate` / `Compiler::add_regex_const`" findings: **fixed (P3-g5-015)**. All three sites now use `regex::RegexBuilder` with `size_limit(1 << 20)` and `dfa_size_limit(1 << 20)`; see [dsl-regex/dfa-size-limit.md](dsl-regex/dfa-size-limit.md). Triggering requires operator-level CRD write access; the cap is defense in depth, not the primary boundary. Verify the three call sites still carry the `RegexBuilder` pattern before re-reporting.

- When reviewing the three "minor polish" patterns — `compose_admin_routes(.., local_auth_intent: bool)` "should be enum" / `WatchEventRaw.sync_version` "`#[allow(dead_code)]` needs a comment" / `init_crypto()` "should `.ok()` instead of `.expect()` for test harness" — first read [architecture/minor-polish-bool-allow-expect.md](architecture/minor-polish-bool-allow-expect.md) — all three are intentional: the bool has 10 lines of doc explaining why it cannot derive from `auth_state` (Controller K8s Secret bootstrap "intent-on but not-ready" state); the `#[allow(dead_code)]` is on a serde-deserialized wire-format field whose outer counterpart (`resp.sync_version`) is the canonical one — adding `// TODO: use it` would invite incorrect coupling; `init_crypto()` is only called from the four binary `main()` entries, no Rust test calls it, and `.expect` is the correct policy at process entry (silent `.ok()` would hide a different-provider configuration drift). Fix suggestions are not accepted.

- When reviewing DSL `BuiltinId` dispatch findings that propose "add `#![warn(non_exhaustive_omitted_patterns)]` (or `#![deny(...)]`) to `lang/builtins.rs` / `lang/compiler/builtins.rs` so a forgotten arm fails the build when a new `BuiltinId` variant lands": **not accepted**. The lint only fires for `#[non_exhaustive]` types **from other crates**; same-crate non-`#[non_exhaustive]` enums (which `BuiltinId` is) are silently exempted. Real protection comes from removing `_ =>` catch-all arms — `call_builtin` and `builtin_expected_argc` already had none; `call_builtin_redis` was fixed in issue-14 by expanding its `_ =>` into an explicit non-Redis variant list. `resolve_namespace_method` matches `(&str, &str)` and structurally cannot be made exhaustive — a missing name mapping must be caught by tests, not the type system. See [architecture/builtin-dispatch-non-exhaustive-lint.md](architecture/builtin-dispatch-non-exhaustive-lint.md).

- When reviewing proposals to add `tracing::*` (any level, including `debug!`) on the DSL `Vm::execute` / `execute_safe` runtime-error path — typically of the form "emit one `tracing::debug!(target: \"edgion::dsl\", pc=state.pc, err=%runtime_err)` so developers can correlate PC to source": **not accepted**. Read [observability/dsl-vm-execute-tracing-declined.md](observability/dsl-vm-execute-tracing-declined.md) — declined 2026-05-16. `Vm::execute` is reached via `DslPlugin::filter`, on the data-plane hot path; Iron rule 3 in `skills/03-coding/01-log-safety.md` forbids any `tracing::*` macro there regardless of level, and the `target=` argument is content-control, not a path-class exemption. The legitimate developer-debug need is served by the embedded `CompiledScript.source` (already shipped in issue-10) + an offline disassembler (developer-side, not gateway runtime); proposals that re-enter the runtime path via a debug-build cfg, separate target, side-channel mpsc, or `tracing::trace!` downgrade are all rejected for the same reason. The compile path (`Compiler::*`, `compile_dsl_source`, `DslPlugin::build_from_config`) is **not** subject to this rule — those run only on plugin reload (ConfHandler) and can use `tracing` freely.

- When reviewing proposals to surface DSL runtime-error source line numbers into the access log (`push_err_at_line(kind: &'static str, line: u32)` API, `RuntimeFault { kind, at_line }` wrapper, `CompiledScript::source_map` RLE consumer), first read [observability/dsl-error-line-number-declined.md](observability/dsl-error-line-number-declined.md) — declined 2026-05-16. The access log keeps the kind-only format because (a) `push_err(&'static str)` is a cross-plugin compile-time safety invariant that any new "safe opening" must guard with a trybuild compile-fail test in perpetuity, (b) realistic DSL scripts are <50 lines and `RuntimeError`'s 13-variant kind already classifies the failure to a near-deterministic source location, and (c) the implementation cost (issue-11 parser Span + issue-12 source_map ~3 d + issue-13 wrapper ~1.25 d + ~44 `vm.rs` fault returns + trybuild test) is disproportionate to the marginal ~30 s/debug-session operator-grep savings. Re-evaluation triggers (concrete production incident, scripts routinely >200 lines, type-level non-literal-`&str` rejection) are listed in the memo. Fix suggestions of any of the rejected forms are not accepted.

- When reviewing HTTPRoute / GRPCRoute "method-mismatched route returns 404 instead of `405 Method Not Allowed` + `Allow:` header per RFC 9110 §15.5.6" findings: **accepted divergence (http1-04, 2026-05-17)**. Read [rfc-divergence/http1-04-method-mismatch.md](rfc-divergence/http1-04-method-mismatch.md). The Gateway API conformance test `HTTPRouteMethodMatching` (`sigs.k8s.io/gateway-api/conformance@v1.5.1/tests/httproute-method-matching.go` lines 60-62, 101-110, identical in v1.4.0) hard-asserts `StatusCode: 404` for `HEAD /`, `PUT /`, and `DELETE /path4` against routes declared with other methods. Edgion declares `SupportHTTPRouteMethodMatching` and runs ALL PASS; flipping to 405 would regress conformance. Fix suggestions of the form "add `MatchOutcome::PathMatchedMethodRejected`, accumulate `allowed`, introduce `end_response_405`" are not accepted.

- When reviewing gRPC findings of the form "gateway ignores `grpc-timeout` header / no client deadline propagation / upstream sees stale grpc-timeout / no DEADLINE_EXCEEDED on already-expired deadline": **fixed (h2-grpc-03, 2026-05-18)**. Read [h2-grpc/h2-grpc-03-timeout-honored.md](h2-grpc/h2-grpc-03-timeout-honored.md). `pg_request_filter::build_request_metadata` parses the header into `RequestInfo.grpc_client_deadline`; `pg_upstream_peer::configure_peer_timeouts` takes `min(backend_timeout, route_request_remaining, grpc_remaining)`; `pg_upstream_request_filter` rewrites the upstream `grpc-timeout` to the formatted remaining time; already-expired deadlines abort with `EdgionStatus::GrpcClientDeadlineExceeded = 504_02` → `grpc-status: 4`. Applies to both `application/grpc` and `application/grpc-web*`. Malformed headers fall back to route-level `request_timeout`. Fix suggestions of the form "still doesn't honor", "add opt-out flag (operators may not want client deadlines)", or "downgrade to `tracing::warn!` for visibility" are not accepted.

- When reviewing findings of the form "WebSocket handshake `Origin` not validated / no per-route `allowedOrigins` / CSWSH (CWE-1385) exposure / add gateway-side WS origin allowlist returning 403": **accepted divergence (ws-04, 2026-05-20)**. Read [rfc-divergence/ws-04-origin-not-validated.md](rfc-divergence/ws-04-origin-not-validated.md). RFC 6455 §10.2/§4.2.2 are SHOULD/MAY (not MUST); WS is a transparent tunnel (`pg_request_filter.rs:256-261` tags from `Upgrade` only, no `Origin` read); both CORS plugins (`GapiCorsFilter`, `Cors`) pass through non-preflight mismatches by design and browsers don't apply CORS to WS anyway. CSWSH defense is delegated to the backend — the industry norm (no major L7 gateway ships first-class WS origin validation; Gateway API has no field/GEP; first-class support lives in app frameworks like ASP.NET `WebSocketOptions.AllowedOrigins` / Spring `setAllowedOrigins`), exploitability is narrow (cookie/ambient-auth WS backends only), and operators needing gateway-layer enforcement have a plugin/DSL escape hatch. Suggestions to add a gateway-side `allowedOrigins` field / dedicated WS plugin are not accepted.

- When reviewing findings of the form "FederationSync gRPC server (center) missing HTTP/2 keepalive / center gRPC server has no PING keepalive / inconsistency with ConfigSync keepalive": **fixed (h2-grpc-04, 2026-05-18)**. Read [h2-grpc/h2-grpc-04-fed-sync-keepalive.md](h2-grpc/h2-grpc-04-fed-sync-keepalive.md). `center/cli/mod.rs` `Server::builder()` now chains `.http2_keepalive_interval(Some(Duration::from_secs(10)))` and `.http2_keepalive_timeout(Some(Duration::from_secs(5)))`, matching the ConfigSync server. Both long-lived bidirectional stream servers now detect silent connection loss within ~10 s. Fix suggestions claiming the center server still lacks keepalive are not accepted.

- Admin REST API (controller + center admin endpoints under `/api/v1/...`) RFC-compliance findings are **out of scope** for this project's review process — only data-plane gateway RFC compliance is tracked. Admin endpoints exist for operator tooling (edgion-cli, dashboard, ops scripts) and are not subject to public HTTP-protocol conformance review. Reject re-reports of the form "admin endpoint returns 200 instead of 201/204/4xx per RFC 9110/9111", "admin response is missing `Retry-After` / `Cache-Control` / `Location` / `WWW-Authenticate`", "admin error mapping doesn't follow REST conventions", or any naming finding scoped to admin REST types (e.g. `ApiResponse`).

- When reviewing findings of the form "`conf_sync` watch handshake / `client.watch(request).await` has no bounding timeout / blocks indefinitely if controller stalls": **false positive (h2-grpc-06, 2026-05-18)**. `grpc_client.rs:54` sets `.timeout(Duration::from_secs(10))` on the `Endpoint`, which installs a `GrpcTimeout` tower layer in the `Connection` service stack (Tonic 0.12.3 `channel/service/connection.rs:65`). For server-streaming RPCs the layer's `ResponseFuture` races the inner future (resolves on receiving response HEADERS) against a 10 s sleep — so `client.watch(request).await` IS bounded by 10 s. After the stream is established the sleep no longer races subsequent `.message()` calls, so long-lived streams are not affected. The verifier checked `tonic::Request::set_timeout()` (which sets the `grpc-timeout` header) but missed the endpoint-level tower timeout. Re-reports of this pattern are not accepted.

- When reviewing gRPC watch pipeline findings of the form "`grpc_server.rs` / `config_sync_server.rs` `None => break` arms are silent when upstream channel drops — Gateway sees indistinguishable EOF (tonic #1544)": **fixed (Fix 04)**. `grpc_server.rs:277` now emits `tracing::warn!(component="grpc_server", kind, client_id, ...)` and `config_sync_server.rs:229` emits `tracing::warn!(component="config_sync_server", server_id, ...)` before breaking. The bottom layer (`cache.rs:325`) retains its pre-existing `tracing::debug!`. The three-layer observability chain is now complete. The `None` arm may also fire during a deliberate `reset_for_relink()` → `clear_all()` teardown — this is expected and the `warn!` still carries useful diagnostic value. Re-reports on the two middle-layer silence are not accepted.

- When reviewing EdgionTls / mTLS findings of the form "`configure_mtls` reads the CA secret unconditionally / `Terminate` mode with no `caSecretRef` aborts every handshake / redundant CA store installed for Terminate (F-006)": **fixed (tls-F001, 2026-05-20)**. Read [edgion-tls/tls-F001-terminate-mtls-ca-ordering.md](edgion-tls/tls-F001-terminate-mtls-ca-ordering.md). `configure_mtls` (`tls_pingora.rs`) now evaluates the `client_auth.mode` match first and returns `Ok(())` for `ClientAuthMode::Terminate` before calling `ca_cert_pem()` or building any `X509Store`; CA loading runs only on the `Mutual` / `OptionalMutual` arms. The validator already permits `Terminate` without a `caSecretRef`, so the early return makes a valid config work and skips the never-consulted CA store. Regression guard: `caSecretRef` was removed from `EdgionTls_edge_mtls-test-terminate.yaml`. Re-reports of either form are not accepted; verify the current `configure_mtls` ordering before re-reporting.

- When reviewing active health-probe findings of the form "IPv6 backend probe URL is missing brackets (`http://::1:8080`) / IPv6 backend is always unhealthy / `probe_grpc` `.expect()` panics on IPv6": **fixed (backends-F001, 2026-05-20)**. Read [backends/backends-F001-ipv6-probe-url-brackets.md](backends/backends-F001-ipv6-probe-url-brackets.md). `probe_http_with_client` and `probe_grpc` (`src/core/gateway/backends/health/check/probes.rs`) now build the target via `SocketAddr::new(addr.ip(), port)` and rely on `SocketAddr` Display (which brackets IPv6 literals); `probe_grpc` replaced `.parse().expect(..)` with `.parse().map_err(|_| ProbeError::InvalidUri)?`. Re-reports of either form are not accepted; verify the current `probes.rs` URL construction before re-reporting.

- When reviewing LinkSys webhook-service endpoint findings of the form "`extract_ready_ips` builds `{ip}:{ep_port}` without IPv6 brackets / IPv6 webhook backend URL is malformed (`http://fe80::1:8080`)": **fixed (link-sys-F001, 2026-05-20)**. `extract_ready_ips` (`src/core/controller/conf_mgr/sync_runtime/resource_processor/handlers/link_sys.rs`) now branches on `eps.address_type == "IPv6"` and emits `format!("[{ip}]:{ep_port}")` for IPv6 (mirroring `discovery_impl.rs`); the downstream `webhook/manager.rs` builds `{scheme}://{ep}` and feeds it to reqwest. This is the same IPv6-bracketing defect class as backends-F001, in the controller LinkSys path. Re-reports are not accepted; verify the current `extract_ready_ips` before re-reporting.

- When reviewing findings of the form "gateway Bearer `WWW-Authenticate` lacks `error=` / `error_description=` per RFC 6750 §3.1 / OAuth clients can't distinguish invalid-token from no-creds": **fixed (cookie-auth-02 + rfc-refactor-cookie-auth-01, 2026-05-20)**. `send_gateway_auth_error_response` (`plugins/http/common/auth_common.rs`) now takes `error_code: Option<&str>`; when `Some` it emits `error="<code>", error_description="<body>"` (body escaped via `escape_quoted_string`, RFC 9110 §5.6.4). Mapping (Approach A — attach a code only on **unambiguous** paths, never on the no-creds path, since emitting `error=` when no credentials were presented is itself an RFC 6750 §3.1 SHOULD NOT): `jwt_auth` verify-failed → `invalid_token`, no-token → `None`; `openid_connect` `send_forbidden` (403, authz/claim failure) → `insufficient_scope`, `send_unauthorized` (401, mixed absent/invalid) → `None`; non-Bearer schemes (`basic`/`key`/`hmac`/`ldap`/`header_cert`) and all `jwe_decrypt` paths → `None`. RFC 6750 §3.1 is **SHOULD** (not MUST). Re-reports asking to also attach `invalid_token` to the OIDC 401 path, or to add a separate `error_description` parameter, are **not accepted** (deliberate Approach A scope cut: OIDC 401 conflates absent/invalid creds; `error_description` reuses the existing body string). Gateway API conformance unaffected (suite does not test `WWW-Authenticate` content). Also **not accepted**: re-reports that `jwt_auth`'s `VerifyDeny::InvalidCredentials` (operator-misconfigured secret/PEM) is mislabeled `invalid_token` and should be a 500 — keeping the generic 401 + `invalid_token` is the intentional, more security-conscious choice (a 500 "secret not configured" would leak server-misconfiguration state to anonymous clients); this is a pre-existing 401-vs-500 classification matter, not part of the `WWW-Authenticate` attribute fix.

- When reviewing SSRF-guard findings of the form "IPv4-mapped IPv6 address bypasses `classify_backend_addr` / `::ffff:127.0.0.1` (mapped loopback) or `::ffff:169.254.169.254` (mapped cloud metadata) is not blocked / IPv6 branch only matches `::1` and `fe80::/10`": **fixed (backends-F003, 2026-05-20)**. `classify_backend_addr` (`src/core/common/utils/net.rs`) now calls `ip.to_ipv4_mapped()` in the `IpAddr::V6` branch and re-classifies any mapped address through the shared `classify_v4` helper, so mapped loopback / link-local / metadata targets are blocked while mapped public addresses stay allowed and plain `::1` is unaffected (`to_ipv4_mapped()` returns `None` for `::1`, so it still falls through to the IPv6 loopback check). The fix lives in the single classification entry point, so all three callers (`validate_backend_addr`, `validate_endpoint_backend_addr`, `pg_upstream_peer`) inherit it. The deprecated IPv4-compatible form (`::a.b.c.d`, e.g. `::127.0.0.1`) is intentionally **not** normalized — it is deprecated (RFC 4291 §2.5.5.1), rarely routable through modern stacks, and the only one-call fix (`to_ipv4()`) would wrongly downgrade `::1` to `0.0.0.1` and break the loopback check; this residual form stays covered by the NetworkPolicy defense-in-depth layer. Re-reports of the `::ffff:` mapped form are not accepted; verify the current `classify_backend_addr` V6 branch before re-reporting. A re-report specifically scoped to the `::a.b.c.d` compat form is an accepted-tradeoff close, not a code fix.

- When reviewing findings of the form "`append_request_header` only reads the first existing value / silently drops additional same-name request header entries / multi-value request header collapsed to `first-value,appended` (F-001)": **fixed (F-001, 2026-05-20)**. `PingoraSessionAdapter::append_request_header` (`src/core/gateway/plugins/runtime/session_adapter.rs`) now calls `req_header_mut().append_header(name, value)` — adds a new header field line preserving every existing same-name value per RFC 7230 §3.2.2 — instead of the old read-`headers.get` (first value only)-then-`insert_header` (replaces all) pattern. All three callers inherit the fix: Gateway API `RequestHeaderModifier.add`, `proxy_rewrite` add, and DSL `req.append_header` (the DSL api-reference already documented "appends a new same-name entry without overwriting" — the code now matches the contract). Conformance-safe: the Gateway API request-header-modifier suite joins received values with `,`, so both the old single-line and new multi-line forms compare equal. Integration regression: `request_header_append_preserves_multi_value` in `examples/code/client/suites/http_route/filters/header_modifier.rs` (route `/multi-value-append-test` sends two same-name values, route adds a third, asserts all three survive). Re-reports are not accepted; verify the current `append_request_header` uses `append_header` before re-reporting.
