# Etcd LinkSys start_health_monitor Reconnect Backoff No Jitter (Thundering Herd)

**Status / verdict**: fixed (link-sys-F004, 2026-05-25)

When reviewing Etcd `LinkSys` reconnect findings of the form "`start_health_monitor` reconnect backoff has no jitter / pure deterministic exponential backoff (500ms→1s→2s→…→30s) / N gateway pods sharing an etcd cluster wake and reconnect in lockstep on a shared outage (thundering herd) / etcd is the only provider without reconnect jitter (link-sys-F004)": **fixed (link-sys-F004, 2026-05-25)**. The reconnect-failure branch of `start_health_monitor` (`edgion-common/src/link/providers/etcd/client.rs`) now applies ±20% multiplicative jitter to the wait: `check_interval = backoff.mul_f64(rand::rng().random_range(0.8..=1.2)).min(max_backoff)`, while `backoff` keeps doubling deterministically (only the sleep instant is jittered, not the doubling sequence). This aligns etcd with the other providers — Redis gets jitter from `fred`'s `ReconnectPolicy::new_exponential`, webhook from `call.rs`. **Use the rand 0.9 API** (`rand::rng()` + `.random_range(..)`, matching `conf_sync/cache_client/event_dispatch.rs:150`) — the issue file's suggested fix used the obsolete rand 0.8 `thread_rng().gen_range(..)` which does not compile in this workspace. Cold path (background health monitor, not data-plane), Low severity (single-pod deployments unaffected; recovery is always eventually guaranteed). No integration test — jitter is non-deterministic timing on a reconnect-failure path, not deterministically assertable; the existing `run_etcd_test.sh` covers connectivity functionally and still passes. Re-reports of the no-jitter / thundering-herd form are not accepted; verify the reconnect-failure branch calls `random_range` before re-reporting.
