# LinkSys Webhook dispatch credential gate (link-sys-F003)

**Status / verdict**: fixed (link-sys-F003, 2026-05-25). Supersedes link-sys-FB04.

When reviewing LinkSys Webhook dispatch findings of the form "`dispatch_full_set` / `dispatch_partial_update` hardcode `ready = true` (`auth_kind = \"NotRequired\"`) for Webhook / Webhook has no credential gate at dispatch / `inject_auth` silently sends an unauthenticated request when the `auth.secretRef` Secret is Pending or Invalid (link-sys-F003)": **fixed (link-sys-F003, 2026-05-25)**. Both Webhook arms in `edgion-gateway/src/link_sys/runtime/store.rs` now compute `let auth = credential::resolved_state(ls); let ready = auth.is_buildable();` and pass `auth.kind()` as the label — identical to the Elasticsearch arm. A webhook whose credential is `Pending` (secretRef set, Secret not yet injected) or `Invalid` (malformed Secret) is no longer registered: `carry_over_if_not_ready` keeps the prior working client (rotation) or skips the build (cold start), and emits the same info-level "not ready" log as the sibling providers. Because dispatch → `WebhookLinkClient::init()` → `manager.upsert()` is the only production registration path, gating here fully closes the bypass; the raw `slot.secret` read in `call.rs::inject_auth` is the symptom, not the origin, and its silent-omit fallback becomes unreachable for the configured-auth case once only `Resolved`/`NotRequired` configs reach the manager. Regression test: `credential.rs` webhook `resolved_state` + dispatch-gate unit tests. The deeper "make `inject_auth` return `Err` on absent material" refactor (call.rs signature + `WebhookCallError` variant) was deliberately **not** taken — it is pure defense-in-depth dead code once the dispatch gate is in place. **Supersedes link-sys-FB04**: the "Webhook `carry_over_if_not_ready` / `preserve_if_not_ready` call is dead code because `ready` is always `true`, remove the guard and the `continue`" finding had it backwards — the hardcoded `ready = true` *was* the F-003 bug; with the gate computing `ready` from `is_buildable()`, the carry-over call is live and load-bearing. Removing the guard would reintroduce the silent-unauthenticated bypass, so that "dead-code cleanup" suggestion is **not accepted**. Re-reports of the hardcoded-`ready=true` / silent-unauthenticated / "remove the redundant webhook gate" form are not accepted; verify both Webhook arms call `credential::resolved_state(ls).is_buildable()` before re-reporting.

## Historical resolution evidence: link-sys-FB04

The finding claimed the Webhook arm of `dispatch_full_set` / `dispatch_partial_update` (`edgion-gateway/src/link_sys/runtime/store.rs`) calls `carry_over_if_not_ready` / `preserve_if_not_ready` with `ready` hard-coded to `true`, so the helper's `if ready { return false; }` early-return makes the `continue` branches (`store.rs:578` / `:688`) dead code. **False — the finding misread the helper's positional arguments.** The literal `true` passed in the Webhook arm is the **4th** parameter `tls_ok` (commented "Webhook TLS material is validated inside build_webhook_client; only auth is gated here"), NOT the **5th** parameter `ready`. The Webhook `ready` is genuinely computed as `credential::resolved_state(ls).is_buildable()`, which returns `false` when `auth.secretRef` is configured but the Secret is still `Pending` (not injected) or `Invalid` (malformed) — so the helper does NOT early-return and the `continue` branch fires, carrying over the existing client (full-set) or preserving live state (partial-update). This is exactly the I5/M4 credential-gating path that mirrors the Elasticsearch arm. Evidence: unit test `resolved_state_webhook_bearer_pending_when_secret_missing` (`credential.rs`) proves Webhook reaches a non-buildable state; the `dispatch_*_skips_build_when_credential_not_ready` / `_invalid` regression tests exercise the same shared helpers; and the closed `link-sys-F008` entry records "Webhook arms intentionally excluded (auth-only gate, `tls_ok` hard-coded true — see link-sys-F003)", confirming `tls_ok` (not `ready`) is the hard-coded literal. No code change. Re-reports of the "Webhook `ready` hard-coded true / carry-over call is dead code" form are not accepted; verify the 4th arg is `tls_ok` and `ready = resolved_state(ls).is_buildable()` before re-reporting.
