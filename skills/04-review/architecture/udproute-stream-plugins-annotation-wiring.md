# UDPRoute `edgion.io/edgion-stream-plugins` annotation wiring (udp-F012)

**Status / verdict**: fixed (udp-F012, 2026-05-26)

When reviewing UDPRoute findings of the form "`edgion.io/edgion-stream-plugins` annotation is silently ignored on UDPRoute / `stream_plugin_runtime` field is never populated or read / no wiring at any of the three layers / a stream plugin (IP allow-list, rate limit) declared on a UDPRoute never runs, with no warning and no status (F-012)": **fixed (udp-F012, 2026-05-26)**. UDP now mirrors the TCPRoute/TLSRoute stream-plugin path: `UDPRouteRule` gained a `stream_plugin_store_key: Option<String>` runtime field (`edgion-resources/src/resources/udp_route.rs`, `#[serde(skip)]`/`#[schemars(skip)]`, additive — no CRD/serialization change); `GlobalUdpRouteManagers::initialize_route` (`src/core/gateway/routes/udp/conf_handler_impl.rs`) resolves it from the `EDGION_STREAM_PLUGINS` annotation via `resolve_stream_plugin_store_key` (identical to TCP/TLS); and `EdgionUdpProxy::handle_client_packet` (`src/core/gateway/routes/udp/edgion_udp.rs`) calls the shared `check_stream_plugins` (fail-close) before backend selection. **Only Stage-1 ConnectionFilter (`spec.plugins`, IP-based) applies** — UDP has no TLS handshake, so `tlsRoutePlugins` never run. Enforcement is **per session, not per packet**: the F-016 session fast-path (`cpu-memory/cases/udp-established-session-route-pipeline-per-packet.md`) returns first for established sessions, so the check runs once at session creation — like TCP's per-connection check, and a denied client never establishes a session (so no fast-path bypass). A mid-session ESP hot-reload-to-deny applies on the next new session / after the ≤60s `SESSION_TIMEOUT`, the accepted session-affinity tradeoff. A rule with no annotation has `store_key == None`, so `check_stream_plugins` returns `Allow` on its first line — the non-annotated path pays one `Option` check only. The rule's older `stream_plugin_runtime` field stays vestigial (TCP keeps its copy too; the real mechanism is `store_key` + dynamic `StreamPluginStore` lookup) — the issue's "use the resolved `stream_plugin_runtime`" wording conflated the two. Option B (controller `warn!` + `ResolvedRefs=False` "unsupported") was **not** taken — there is no technical reason UDP cannot support stream plugins when TCP/TLS do, and a capability gap across the L4 route family is worse than parity. Docs updated: `annotations-metadata.md`, `00-annotations-overview.md`, `14-edgion-stream-plugins.md`. Re-reports of the silently-ignored / never-wired form are not accepted; verify `handle_client_packet` calls `check_stream_plugins` and `initialize_route` resolves the store key before re-reporting.
