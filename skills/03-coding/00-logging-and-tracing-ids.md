# Log ID propagation rules

> Goal: when any request fails, the log can be filtered to surface both the **control-plane** and **data-plane** records simultaneously.

## Core ID triple

| ID | Meaning | Source | Control plane | Data plane |
|----|------|------|--------|--------|
| `key_name` | Resource unique identifier `namespace/name` | `ResourceMeta::key_name()` | All logs | access log (`rns`/`rn` or `ns`/`name`) |
| `rv` (resource_version) | K8s resource version | `ResourceMeta::get_version()` / `metadata.resource_version` | Key logs | Not needed |
| `sv` (sync_version) | gRPC sync version | `edgion.io/sync-version` annotation | When sending via gRPC | access log / match info |

## Architecture: lifecycle of sv

```
Controller                         Gateway (Data Plane)
┌──────────────────┐               ┌──────────────────────────┐
│ ResourceProcessor│               │ event_dispatch.rs        │
│   process_resource()             │   list_and_reset()       │
│   ① generate sv (early)         │     ↓ set_sync_version() │
│   ② info_span(rv, sv, ...)      │   watch loop             │
│         ↓                        │     ↓ set_sync_version() │
│ ServerCache.apply_change(sv)     │         ↓                │
│   use provided sv                │ ConfHandler.full_set()   │
│         ↓                        │   / partial_update()     │
│ gRPC WatcherEvent                │         ↓                │
│   {type, sync_version, data}  ──►│ Route mgrs / TlsStore    │
│                                  │   get_sync_version()     │
│                                  │         ↓                │
│                                  │ MatchInfo.sv / MatchedInfo.sv
│                                  │         ↓                │
│                                  │ AccessLog (sv field)     │
└──────────────────┘               └──────────────────────────┘
```

**sv generated early**: sv is generated at the entry of `process_resource()` via `next_resource_version()`, not inside `apply_change()`. This way the spans across the entire processing flow carry sv, so Controller and Gateway logs can be correlated by the same sv in one step. `apply_change` accepts `sv: Option<u64>`: if provided it is used, otherwise it is generated internally.

## How sv is stored

**Use `metadata.annotations["edgion.io/sync-version"]`**:

- Applies uniformly to all synced resources (including Service and EndpointSlice)
- No need to modify the Spec struct
- Injection point is `event_dispatch.rs` (both List and Watch paths)
- Read via `ResourceMeta::get_sync_version()` (auto-generated by macro)

```rust
// Inject (event_dispatch.rs)
edgion_resources::resource::meta::set_sync_version(resource.meta_mut(), sv);

// Read
let sv = resource.get_sync_version(); // From the ResourceMeta trait
```

## Control-plane logging rules

`processor.rs`'s `process_resource()` / `process_delete()` use `info_span` + `.instrument()` to wrap the entire processing flow; the span automatically carries `kind/name/ns/rv/sv`.

**Logs inside the span do not need to repeat these fields** — only write the message and any extra fields:

```rust
// span automatically provides kind/name/ns/rv/sv
tracing::warn!(error = %error, "Resource validation error");

// No longer needed (already in the span)
tracing::warn!(kind = self.kind, name = %name, namespace = %namespace, rv, ...);
```

Each Handler's `parse()` / `on_change()` runs inside the span and inherits these fields automatically. Logs recorded outside the span still need to include `kind` + `key_name` + `rv` manually.

## Data-plane logging rules

The data plane does not use `tracing::*` for request-level logs (see [01-log-safety.md](01-log-safety.md)); they go through the access log instead.

### HTTP / gRPC routes

The `MatchInfo` struct carries `sv` automatically, injected from `route.get_sync_version()` at route compilation time:

```rust
MatchInfo::new(ns, name, rule_id, match_id, match_item, route_sv)
```

**HTTP/gRPC route metadata (`rsc.labels`) is always `None`** — the
`edgion.io/log-label.<suffix>` prefix is narrowed to TLSRoute / EdgionTls only
and is not resolved for HTTPRoute/GRPCRoute at all (see
`crate::extract_log_labels`'s doc at `edgion-gateway/src/ctx.rs`). On
HTTP/gRPC, projecting route metadata into the access log goes through an
`AccessLogExtern from: routeLabel` / `from: routeAnnotation` declaration
instead, resolved at `logging()` from route metadata retained on the match
unit — not through `log_labels`/`rsc.labels`.

`log_labels` (`Option<LogLabels>`, keys prefixed `edgion.io/log-label.`,
serialized under `rsc.labels`) still exists for **TLSRoute and EdgionTls**,
resolved **at resource-parse time, never on the data path**. The single
resolver + guardrails live in
`edgion_resources::resources::common::resolve_log_labels`; the gateway
`extract_log_labels(&metadata)` is a thin wrapper used at `TlsRouteUnit::from_route`
(TLSRoute). `EdgionTls` instead caches the resolved map in
`EdgionTlsSpec::resolved_log_labels` during `pre_parse`, and the handshake
callback only `LogLabels::from_resolved`-wraps the cached `Arc` (no
per-handshake scan). See `skills/03-coding/observability/00-access-log.md`.

### TLS / TCP / Stream routes

The `MatchedInfo` struct carries `sv`:

```rust
MatchedInfo { kind, ns, name, section, sv: resource.get_sync_version() }
```

### Backend MatchedInfo

The `sv` of a backend MatchedInfo (in the upstream) is set to 0 — backend resources (Service) have their own sv, but it is unrelated to route matching.

## Cross-resource sv tracking

**Problem**: Secret is not synced to the data plane; EdgionTls depends on Secret — how is it tracked?

**Answer**: Naturally resolved via the dependency requeue mechanism:

1. Secret changes → `SecretRefManager` → requeue EdgionTls
2. EdgionTls re-runs `parse()`, fetches the latest Secret, fills it into `spec.secret`
3. The `process_resource()` entry generates sv and passes it to the cache via `apply_change(Some(sv))`
4. The data plane receives the updated EdgionTls carrying the new sv

The same applies to all dependency relationships:

| Dependent | Dependency | Requeue mechanism | sv update |
|--------|---------|-------------|---------|
| EdgionTls | Secret | SecretRefManager | EdgionTls gets a new sv |
| Gateway | Secret | SecretRefManager | Gateway gets a new sv |
| HTTPRoute | Service | ServiceRefManager | HTTPRoute gets a new sv |
| EdgionPlugins | Secret | SecretRefManager | EdgionPlugins gets a new sv |
| EdgionPlugins | ConfigMap | Shared bidirectional/SecretRefManager reference index | EdgionPlugins gets a new sv |
| TLSRoute | Gateway | GatewayRouteIndex | TLSRoute gets a new sv |

## Troubleshooting example

```bash
# 1. Find sv from the access log
# access.log: {"match_info":{"rsc":{"kind":"HTTPRoute","ns":"prod","name":"api-route"},"sv":42},...}

# 2. Filter data-plane conf_sync logs by sv
grep 'sv.*42' gateway.log

# 3. Use rsc identity + sv to locate the Controller processing span.
# rv exists only in control-plane logs; it is not an access-log field.
grep 'sv.*42' controller.log

# 4. If the issue is caused by a Secret change (EdgionTls cert update)
# Find EdgionTls's new sv, then trace back the Secret requeue and EdgionTls reprocess in the controller log
```
