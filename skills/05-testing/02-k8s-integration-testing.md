# Edgion K8s Integration Testing Guide

> See `/Users/caohao/ws1/Edgion/skills/integration-testing.md` for the base workflow. This file only covers **the differences and modifications required for the Kubernetes scenario**.

## 1. Goal and scope

This guide is for migrating the existing local-process integration tests to a K8s environment. The focus is on:

- Configuration layer: `examples/test/conf` -> `examples/k8stest/conf`
- Execution layer: local processes -> K8s Deployments/Services
- Assertion layer: fixed IP/port assumptions -> Service/EndpointSlice dynamic behavior

## 2. Core differences from the original integration tests

| Dimension | Original mode (local process) | K8s mode |
|---|---|---|
| Process model | `start_all_with_conf.sh` brings up controller/gateway/test_server | Pod lifecycle managed by Deployment |
| Backend addressing | `127.0.0.x` / `localhost` / fixed port | `*.svc.cluster.local` + Service port |
| Endpoint resources | Often hand-written `Endpoint/EndpointSlice` fixtures | Should not be hand-maintained; auto-generated by K8s based on Service selector |
| Number of available instances | Often fixed and predictable | Pod IPs change after rebuild/scaling |
| Config loading | Apply original conf directly | Conf must be K8s-ified (backend/service semantic conversion) |
| Test assertions | Can assert fixed IPs | Should assert "belongs to current endpoint set / matches the distribution" |

## 3. K8s networking and test constraints

### 3.1 Endpoint/EPS is no longer a config input

- The test configuration must not maintain `kind: Endpoint` / `kind: EndpointSlice`.
- Keep only Service + Deployment (or StatefulSet).
- For multi-replica behavior (RR/CH), increase the test-server replica count instead of hard-coding endpoint IPs.

### 3.2 Upstream addresses and ports

The original typical upstreams:

- `127.0.0.1:30001`~`30005`
- `localhost:30040`

Recommended K8s mode:

- `edgion-test-server.edgion-test.svc.cluster.local:<port>`
- Or a short service name in the same namespace (ensure DNS resolution scope is consistent)

### 3.3 Assertion strategy changes

- Do not assert "must be a specific fixed IP" any more.
- Assert instead:
  - The IP is in the current endpoints set
  - Or verify the distribution via metrics (RR/CH)
  - Or verify functional logic via header/body without binding to an instance address

## 4. Current state of the repo

### 4.1 `examples/k8stest/conf` is now the K8s test baseline

K8s integration tests now use `examples/k8stest/conf` as the sole configuration source and remain mostly isomorphic to the shared suites of `examples/test/conf`. Note that a small class of **runtime-managed Secret templates** in the K8s directory keep `data: {}` empty in the file itself; the actual content is generated under `examples/k8stest/generated/secrets/` during the prepare phase before being applied.

Constraints to keep in mind:

- `HeaderCertAuth`'s `header-cert-ca` is a runtime-managed Secret and must not be overwritten by static templates applied recursively.
- `ref-grant-status` reuses the existing test namespace; no extra `app` / `other` is created.
- `HTTPRoute/Match`'s wildcard host must match the shared test code: `*.wc-match-test.example.com`.

### 4.2 The execution chain and config source are settled

`/Users/caohao/ws1/Edgion/examples/k8stest/scripts/run_k8s_integration.sh` is now the sole entry point for K8s integration tests. prepare / conf apply / test-client batch all run around `examples/k8stest/conf` and no longer rely on an external deploy repo loading `examples/test/conf`.

## 5. What must be changed for new conf (landing checklist)

### 5.1 Directory and naming alignment (P0)

- Add same-named suite directories under `examples/k8stest/conf` that match `examples/test/conf`.
- `LBPolicy` is split or mapped to:
  - `HTTPRoute/Backend/LBRoundRobin`
  - `HTTPRoute/Backend/LBConsistentHash`
- Add `EdgionPlugins/base` and all plugin subdirectories.

### 5.2 Resource-content conversion (P0)

- Remove/forbid Endpoint and EndpointSlice documents.
- All backendRefs point to a Service (name + port).
- Provide a separate Deployment (3 replicas recommended) for backends that need multi-instance testing.
- Keep non-backend semantics of Gateway/Route as unchanged as possible (host/match/filter remain consistent).
- For certificate-related tests use a runtime-managed Secret template: keep `data: {}` empty in the template, with the real value generated in the prepare phase.
- When recursively applying the full conf, the runtime-managed Secret templates must be excluded so that the real certificates generated by prepare are not overwritten.

### 5.3 Namespaces and base resources (P0)

Recommend fixing four test namespaces:

- `edgion-system`: controller/gateway/RBAC/CRD related
- `edgion-default`: route and plugin configuration resources (default test config)
- `edgion-test`: test-server/test-client/service
- `edgion-backend`: cross-namespace backend / ReferenceGrant scenarios

And ensure the minimal base conf is complete:

- `GatewayClass`
- `EdgionGatewayConfig`
- TLS Secret / ReferenceGrant required by tests

Additional constraints:

- The `default` namespace must not contain test resources after run; cleanup may only keep system objects such as the built-in `kubernetes` Service.
- Scenarios such as `ref-grant-status` and `AllowedRoutes/Selector` should reuse the four namespaces above instead of introducing extra test namespaces.

### 5.4 K8s-dependent scenarios (P1)

- Suites depending on external services like LDAP, OIDC, ForwardAuth, WebhookKeyGet must provide the corresponding Service in K8s.
- If a suite still depends on host-side containers (docker compose), label it as "non-pure-K8s suite".

## 6. What to add / change in suites

### 6.1 Mandatory rework (P0)

The following types of suites must be rewritten to be "environment-agnostic":

- No hard-coded `http://127.0.0.1:<port>`.
- Use `TestContext` uniformly (`ctx.target_host` + `ctx.*_port`) to construct URLs.
- Use `ctx.metrics_client()` for metric scraping; do not hard-code `127.0.0.1:5901`.

### 6.2 Key suite rework (P0/P1)

- `DirectEndpoint`: currently only supports single-IP injection (`EDGION_TEST_DIRECT_ENDPOINT_IP`); extend to "fetch the endpoint list from the Admin API and pick a valid IP".
- `AllEndpointStatus`: switch assertions to set/statistics-based to avoid depending on fixed instances.
- `HTTPRoute/Backend/LBRoundRobin`, `LBConsistentHash`: distribution assertions based on the real-time endpoint set.
- `Gateway/StreamPlugins`, `TCPRoute/StreamPlugins`: avoid host-loopback-specific assumptions.
- `DynamicExternalUpstream`: split the `localhost` loopback-rejection scenario into a local-only case; do not treat it as a default K8s passing condition.

### 6.3 Recommended new suites (K8s-specific)

- `K8S/ServiceRollingUpdate`: validates routing and retry behavior during Pod rotation.
- `K8S/EndpointChurn`: validates DirectEndpoint / load-balancing behavior under endpoint adds and removes.
- `K8S/NamespaceIsolation`: validates cross-namespace backendRef + ReferenceGrant behavior.

## 7. Execution suggestions (get it working before getting it complete)

Roll out in stages:

1. P0: `HTTPRoute/Basic/Match/WeightedBackend/Timeout`, `GRPCRoute/Basic/Match`, `UDPRoute/Basic`, `EdgionTls/*`.
2. P1: `EdgionPlugins` core plugins (Jwt/Jwe/Hmac/HeaderCert/KeyAuth/BasicAuth/RateLimit/RealIp).
3. P2: `DirectEndpoint/AllEndpointStatus/StreamPlugins/Ldap/OpenidConnect`.

### Recommended execution model (already implemented in scripts)

- Phase 1: `prepare`
  - Verify that `k8stest/conf` contains no Endpoint/EndpointSlice
  - Generate runtime Secret YAML (e.g., the `HeaderCertAuth` CA)
  - Apply the full config strictly (exit on failure)
  - After apply, restart the gateway uniformly and wait for ready
- Phase 2: `run tests`
  - Only execute test_client suites; do not restart the gateway per suite

Corresponding script:

- `/Users/caohao/ws1/Edgion/examples/k8stest/scripts/run_k8s_integration.sh`
  - `--prepare-only`: only prepare the environment
  - `--skip-prepare`: only run tests
